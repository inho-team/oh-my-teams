# 적응형 팀 편성 첫 파동 설계 (Adaptive Staffing Design Wave 1)

문서 revision: 6

## 1. 현행 구조 및 설계 계약

현행 체계를 실제 파일과 함수명, 제약 조건 인용으로 설명하고, 제안하는 설계를 명확히 구분하여 서술합니다.

### 1.1 상설 조직 역할별 고정 모델 제거 (완료 조건 1)
- **현행**: `plugins/oh-my-teams/schemas/organization.schema.json`에서 `roles` 객체 (구체적으로 `#/$defs/role_profile` 스키마 부분)는 `pm`, `pl`, `senior`, `junior` 각 역할에 대해 정적인 `profile` 문자열 식별자를 강제로 바인딩합니다.
- **제안**: 상설 조직의 정본은 역할별 고정 모델표가 아닌, 사용 가능한 실행기와 구독 자원(`pool`), 허용 정책, 동시 실행 한도로 정의합니다. 사용자가 역할별 모델을 고르지 않게 변경합니다.

### 1.2 카탈로그 기반 조직 결성 (완료 조건 2)
- **현행**: `plugins/oh-my-teams/skills/form/SKILL.md` (form 스킬)은 내장된 고정 목록이나 사용자 질문을 통해 모델을 배정하여 초기 `organization.json` 초안을 작성합니다.
- **제안**: 조직 결성 스킬(`form`) 실행 시 설치된 모델 카탈로그와 인증 상태를 조회하여 사용 가능한 구독 자원만 확인합니다. 카탈로그 조회 실패를 내장 목록이나 임의 기본값으로 대체하지 않습니다. 이 변경은 선행 카탈로그 작업이 병합된 이후 두 번째 파동에서 적용됩니다.

### 1.3 이사의 PM 선택 (완료 조건 3)
- **현행**: `plugins/oh-my-teams/scripts/teams-org.mjs`의 `launchContext` 함수는 워크플로 스냅샷이나 지정된 조직 파일을 단순히 반환할 뿐이며, 브리프 복잡도를 바탕으로 PM 프로필을 동적으로 결정하거나 그 결정을 기록하지 않습니다.
- **제안**: 이사(Director)는 kickoff 브리프의 목표 복잡도와 위험도를 평가하여 PM 프로필과 추론 강도를 선택합니다. 이 결정은 선택 당시의 카탈로그 revision, 허용 자원, 선택 이유와 함께 기록됩니다. PM은 자기 프로필을 임의로 변경할 수 없습니다.

### 1.4 PM의 하위 역할 선택 (완료 조건 4)
- **현행**: `plugins/oh-my-teams/scripts/role-launch.mjs`의 `roleProfileId` 함수는 정적으로 `org.roles[role].profile` 필드를 읽어 반환하거나 지정된 프로필이 폴백(`fallbacks`)에 포함되어 있는지 확인하는 역할만 수행합니다.
- **제안**: 워크플로 기록 안에서 PM이 task별로 필요한 실행 깊이와 하위 역할(PL, Senior, Junior)의 프로필을 동적으로 선택하도록 지원하며, `roleProfileId` 함수는 해당 워크플로의 동적 선택 결과를 반영하도록 수정합니다. 필요하지 않은 역할은 생략합니다.

### 1.5 감사 독립성 유지 (완료 조건 5)
- **현행**: 워크플로에서 감사(Audit) 역할의 독립성 보장이 `organization.schema.json`에 명시적으로 분리되어 있지 않습니다.
- **제안**: 이사 또는 검증된 독립 정책이 감사를 배정하며, PM은 감사의 신원, 주 프로필, 판정 권한을 선택할 수 없습니다. 단, 이 규칙을 일반적인 검토(Review) 역할 전체의 배정 금지로 확대하지 않습니다. 일반 검토 역할은 기존 방식처럼 배정될 수 있습니다.

### 1.6 지능형 모델 승격과 선택 (완료 조건 6)
- **현행**: 작업의 예상 재작업이나 위험도에 따라 모델을 동적으로 승격하는 논리가 없습니다.
- **제안**: 모델 선택기는 가장 싼 모델을 무조건 고르지 않고, 재작업이나 통합 충돌 위험이 크면 상위 프로필을 선택합니다. 이때 모델의 이름이나 추론 강도의 이름으로부터 비용이나 능력의 고정된 순위를 만들지 않습니다. 승격과 강등의 근거는 기계적으로 검증 가능한 기록으로 남깁니다.

### 1.7 PM 승격 관문 (완료 조건 7)
- **현행**: 지정된 예산과 자원을 초과하여 다른 프로필로 승격할 때 승인을 요구하는 관문이 없습니다.
- **제안**: PM이 최초 승인 자원보다 비싼 프로필이나 새 계정으로 승격하고자 할 때 이사의 결정이 필요합니다. 동일한 `pool`의 소진을 다른 프로필로 우회하지 않습니다.

### 1.8 스냅샷 보존 (완료 조건 8)
- **현행**: `plugins/oh-my-teams/scripts/workflow.mjs` 및 `workflow-store.mjs`의 생성, 스냅샷, 재개, 전달 로직은 역할별 프로필 선택 결정이나 카탈로그 스냅샷을 불변으로 함께 보존하지 않습니다.
- **제안**: kickoff와 워크플로는 선택 당시의 구독 자원 스냅샷, 카탈로그 근거, PM 선택 및 task별 역할 결정을 기록합니다. 재개 시 이 불변 스냅샷을 바탕으로 실제 실행 모델을 복원합니다.

### 1.9 실질 토큰 효율 측정 (완료 조건 9)
- **현행**: `plugins/oh-my-teams/scripts/usage.mjs`의 `normalizeTokenUsage` 함수는 Agy 대화형 세션처럼 측정이 불가능한 사용량을 다루는 정밀한 구별 기준이 부족합니다.
- **제안**: 실제 입력과 출력 토큰, 캐시 여부, 호출 수, 재작업 횟수를 기준으로 효율을 평가합니다. 대화형 세션처럼 측정이 불가능한 사용량은 `unknown`으로 별도 표시하며, 이를 추정 토큰 수치나 최소 가중치 혹은 0으로 대체하지 않습니다.

### 1.10 구형 조직 호환 이전 (완료 조건 10)
- **현행**: `plugins/oh-my-teams/scripts/core.mjs`의 `validateOrg` 함수는 구형 데이터를 만나면 조용히 마이그레이션하지 않고 오류를 발생시켜 거부(`validateOrg refuses it instead`)합니다.
- **제안**: 구형 데이터를 이전할 때 개정 숫자에 의존하지 않고, 명시적인 스키마 구조와 필드 형식을 기준으로 구별하여 이전 호환성을 확보합니다. 이전 과정에서 기존 프로필, `pool`, 폴백(`fallback`), 사용 한도와 권한을 보존하며, 새로운 자원을 추측하여 임의로 추가하지 않습니다. 진행 중인 스냅샷은 그대로 실행합니다.

### 1.11 회귀 테스트 (완료 조건 11)
- **제안**: 정상 선택, 역할 생략, 위험 상승 승격, 권한 없는 PM 자기 승격 시도 방어, 감사 독립성 위반 방어, 카탈로그 변경 및 조회 실패, `pool` 소진, 스냅샷 불변 재개, 구형 조직 호환 이전, 측정 불가 사용량의 구별 시나리오를 각각 검증하는 회귀 테스트를 작성합니다.

### 1.12 문서 일관성 (완료 조건 12)
- **제안**: `form`, `adjust`, `kickoff`, 역할 명령, 조직 스키마와 사용자 문서가 새로운 계약을 일관되게 설명하도록 갱신합니다. 런타임에서 강제하는 선택 규칙을 스킬 문서에 중복하여 서술하지 않습니다.

### 1.13 Eval 평가 근거 (완료 조건 13)
- **제안**: 구현 전후의 대표 시나리오에서 호출 수, 측정 가능한 토큰, 재작업 횟수, 선택된 역할을 비교하는 eval 자료를 생성합니다. 품질 기준을 낮춰 토큰 수치만 줄이는 결과는 수용하지 않습니다.

### 1.14 코드 품질 (완료 조건 14)
- **제안**: 수정된 코드는 `npm run format`과 `npm run sync`를 거친 후, `npm run lint`와 `npm test`를 통과해야 합니다. 무거운 검사를 실행하기 전에는 자원 슬롯을 확보하고 종료 후 해제합니다.

## 2. 실행 순서와 의존성

1. **첫 번째 파동**: 현재 조직 스키마의 실제 필드, `validateOrg`와 구형 이전 호출 경계, `roleProfileId`와 `launchContext`의 스냅샷 해석, workflow 불변성, 사용량 정규화와 폴백 경로 등을 조사하고 설계 계약과 이전 계획을 작성합니다. 이 파동에서는 아직 구현되지 않은 카탈로그 인터페이스나 `form`, `adjust` 스킬을 직접 편집하지 않습니다.
2. **두 번째 파동**: 선행 카탈로그 기능이 `main`에 병합된 이후에 그 API를 소비하여 구독 자원 목록과 이사의 PM 선택 경로를 구현합니다. 이 파동은 `form` 스킬의 구독 자원 등록 기능과 역할별 모델 사전 선택 질문을 제거하는 작업까지 책임집니다. `pool` 스키마, 인증 확인, 역할 선택 정책, 구형 조직 이전 구현도 두 번째 파동이 소유합니다. 선행 카탈로그 kickoff가 이 파동을 기다리는 의존성 순환을 만들지 않습니다.
3. **세 번째 파동**: PM의 하위 프로필 선택, 승격 관문, 스냅샷 기록, 사용량 집계 및 구형 조직 이전 구현을 완성합니다. 정형 문서 계약과 이슈 #139의 감사 계약을 별도의 독립 관문(gate)으로 남겨두고, 문서 식별자와 개정 계약이 확정된 이후에 그 규칙을 사용합니다.

## 3. 비목표

- 이사를 PM, PL, Senior, Junior와 같은 실행 역할 그래프에 넣지 않습니다.
- PM이 감사 역할이나 감사 판정 권한을 선택하도록 만들지 않습니다.
- 모델 능력이나 가격, 토큰 효율을 이름만으로 고정하여 서열화하지 않습니다.
- 동적 모델 카탈로그 개시 작업이나 `.omt` 정형 문서 개시 작업의 독립 구현을 이 개시 작업에서 다시 만들지 않습니다.
- 진행 중인 개시 작업의 모델과 역할을 새로운 정책으로 다시 배정하지 않습니다.
- 품질, 보안, 검토 독립성을 낮추어 토큰 수치만 줄이지 않습니다.
- 사용자 동의 없이 원격 저장소 푸시(push), 풀 리퀘스트(PR) 생성, 외부 배포나 새로운 과금 계정 사용을 하지 않습니다.
