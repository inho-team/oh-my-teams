## 1. 결정 제안

**다음 평가의 기준선은 Agy Claude Opus 4.6 중심으로 잡고, Sonnet과 GPT-OSS를 섞는 경로가 실제로 더 나은 작업 유형에만 혼합 운영을 적용한다.**

현재는 GPT-OSS 사용 비율을 높이는 것보다 같은 공유 할당량으로 정확한 결과를 더 많이 완료하는 것이 목적이다. Opus를 모든 호출에 영구 고정하거나 세 모델의 호출 비율을 임의로 나누지 않는다.

1. 설계·복잡한 구현·중요한 검토는 Opus를 기본 후보로 삼는다.
2. 범위가 정해진 일반 구현은 Sonnet을 비교 후보로 둔다.
3. GPT-OSS는 짧은 편집·정확한 인용·결정적으로 검증 가능한 초안에서 우선 평가한다.
4. 모델이 필요 없는 보고 취합·증거 대조·조직도·검사 실행은 스크립트로 처리한다.
5. 직급과 모델은 분리한다. Intern에게 Opus를 배정할 수 있고, Senior의 기계적 자료 수집에 GPT-OSS를 사용할 수 있다.

기본 예제의 `Intern: GPT-OSS → Sonnet` 경로와 `opus-first`, `balanced` 프리셋은 모두 구현돼 있다. 사용자의 실제 조직에 적용할 때는 `preset --apply` 또는 `org-edit`으로 바뀌는 항목만 확인한다. 조직을 매번 재구성하거나 기존 구독 선택을 다시 묻지 않는다.

## 2. 판단 근거와 확인되지 않은 것

### 2.1 사용자 제공 할당량 화면

사용자가 제공한 화면에는 다음이 표시되어 있다.

| 항목 | 표시값 |
|---|---|
| 그룹 | CLAUDE AND GPT MODELS |
| 포함 모델 | Claude Opus, Claude Sonnet, GPT-OSS |
| 주간 잔여량 | 95.84% |
| 주간 갱신까지 | 47시간 20분 |
| 5시간 잔여량 | 92.32% |
| 5시간 갱신까지 | 4시간 9분 |

이 값은 사용자가 전달한 시점의 스냅샷이다. 현재 시각에도 같은 값이라고 가정하지 않으며, 상대적인 갱신 시간으로 정확한 서버 갱신 시각을 만들어내지 않는다.

확인 가능한 해석:

- 화면에서 세 모델이 같은 그룹으로 묶여 있다.
- 표시 당시 두 창 모두 잔여량이 충분해 보인다.
- Opus를 추가 평가할 여유가 있다는 운영 판단은 가능하다.

이 화면만으로 확인할 수 없는 것:

- 세 모델이 토큰당 동일한 할당량을 차감하는지.
- 실험 전 잔여량이 얼마였는지, 표시된 사용분 중 실험이 차지한 양.
- 호출·추론·캐시·모델별 가중치와 반올림 방식.
- 같은 구독을 사용하는 다른 세션의 영향과 표시 지연.
- Gemini 모델의 풀과 차감 방식.
- native Claude 또는 Codex 구독과 Agy 그룹의 관계.

따라서 `100 - 95.84` 또는 `100 - 92.32`를 이번 실험의 사용량으로 계산하지 않는다. 그룹에 함께 있다는 사실도 모델 간 비용 동일성을 증명하지 않는다.

### 2.2 기존 모델 비교

동일한 Agy CLI와 기준 커밋에서 두 과제를 비교했다. 각 모델의 최초 입력은 작업별로 같았으며, GPT-OSS의 실패 과제에만 오류 설명을 추가해 한 번 재시도했다.

| 모델 | 최초 통과 | 완료까지 호출 | 최종 통과 | 누적 토큰 | 모델 호출 시간 합계 |
|---|---:|---:|---:|---:|---:|
| GPT-OSS-120B | 1/2 | 3 | 2/2 | 37,203 | 50.88초 |
| Claude Sonnet 4.6 | 2/2 | 2 | 2/2 | 34,164 | 37.27초 |
| Claude Opus 4.6 | 2/2 | 2 | 2/2 | 33,493 | 41.00초 |

이번 두 과제의 완료 기준에서는 Claude 두 모델이 재시도를 포함한 GPT-OSS보다 토큰을 적게 사용했다. Sonnet의 호출 시간 합계가 가장 짧았고 Opus의 총 토큰이 가장 적었다. 별도의 좁은 경계값 수정에서는 GPT-OSS가 1회, 11,845토큰으로 성공했다.

한계:

- 표본은 작은 함수 두 개이며, 장기 저장소 탐색·다중 파일 통합·일반적인 개발 생산성을 증명하지 않는다.
- 최초 프롬프트가 같아도 모델별 기본 문맥과 토크나이저가 다를 수 있다.
- 토큰은 Agy가 보고한 사용량이며 실제 금액·구독 차감량은 측정되지 않았다.
- 병렬 비교의 호출 시간 합계와 사용자가 기다린 전체 벽시계 시간은 다르다.

## 3. 비교할 운영 프리셋

### A. opus-first — 다음 평가의 기준선

Agy 그룹 내 실제 모델 작업은 Opus를 우선 배정한다. 기존 PM/PL의 Claude·Codex 계정 선택은 그대로 두고, Agy 작업 프로필만 이 프리셋의 비교 대상으로 한다. 모든 역할을 Agy로 강제 이전하지 않는다.

| 업무 | 기본 처리 |
|---|---|
| 설계·분할 경계 판단·복잡한 코드 수정 | Opus |
| 의미 검토·통합 충돌 | Opus |
| 일반 구현·제한 편집 | Opus로 기준선 측정 |
| 증거 취합·상태·검사 실행 | 스크립트 |

장점은 모델 선택과 승격 판단이 단순하고, 약한 첫 시도의 실패 비용을 피할 수 있다는 것이다. 단점은 작은 작업에서도 Opus의 지연과 차감량이 불필요할 수 있다는 것이다. 이 차이는 실측으로 확인한다.

### B. balanced — 업무별 혼합 운영

| 업무 조건 | 첫 모델 | 실패 처리 |
|---|---|---|
| 설계·여러 모듈의 계약·중요한 의미 검토 | Opus | 원인 분류 후 재분할 또는 필요한 수정 |
| 명확한 완료 조건이 있는 일반 기능·버그 수정 | Sonnet | 구현 실패이면 Opus로 승격 |
| 작은 문자/경계 수정·인용 수집·구조화 초안 | GPT-OSS | 한 번 실패하면 Sonnet 또는 Opus |
| 단순 보고 조립·조직도·검증 중복 제거 | 모델 호출 없음 | 입력이나 검사 오류를 직접 보고 |

GPT-OSS에 배정하려면 수정 범위와 검증 조건이 모두 명확해야 한다. 설계 판단이나 넓은 저장소 탐색이 선행돼야 하면 바로 Sonnet/Opus에 배정한다. 후보 인용은 실제 파일과 대조하고, 초안의 판단을 그대로 최종 판정으로 올리지 않는다.

고정된 `Opus 20% / Sonnet 40% / GPT-OSS 40%` 같은 비율 목표는 두지 않는다. 혼합 비율은 작업 구성에 따라 달라지는 결과 지표다.

### C. 기존 GPT-OSS 우선 — 대조군

현재 구현된 한 번 시도 후 선택된 모델로 승격하는 경로를 대조군으로 유지한다. 이전의 고정 5회 재시도는 복원하지 않는다. 단순 과제에서 유리한지, 실패 후 상위 모델을 호출하는 과제에서는 총량이 증가하는지 분리해 평가한다.

## 4. 모델 배정과 승격 규칙

### 4.1 직급과 구독

- 조직은 `pm/pl/senior/junior/intern` 구조를 유지한다.
- 모델 경로는 각 역할이 선택한 구독 프로필 안에서만 바뀐다.
- 별도 native Claude/Codex 계정이나 Gemini 구독으로 이동하는 것은 같은 풀 안의 모델 전환과 구분한다.
- 새로운 프로필을 사용하려면 `org-edit`에서 해당 변경만 설정한다. 이미 지정된 fallback은 다시 질문하지 않는다.
- 실행 당시의 조직 revision과 모델 배정 스냅샷을 고정하고 진행 중 작업에 설정 변경을 소급하지 않는다.

### 4.2 오류별 처리

| 오류 | 처리 |
|---|---|
| GPT-OSS의 JSON 형식·예시 문구·부정확한 편집 | 같은 입력을 여러 번 반복하지 않고 지정한 상위 모델로 승격 |
| Sonnet의 재현 가능한 구현 실패 | 실패 출력과 현재 파일 상태만 전달해 Opus로 승격 |
| Opus의 구현 실패 | 오류를 분류하고 필요한 한 번의 수정 또는 PL 재분할; 무한 반복 금지 |
| 검사 도구 없음·fixture 오류 | 환경 문제로 분리; 모델 교체를 해결책으로 사용하지 않음 |
| 모델 자체의 일시적 서비스 오류 | 공급자가 확인 가능한 오류 정보에 따라 제한된 재시도 또는 대체 |
| 공유 그룹 할당량 소진 | 같은 그룹의 다른 모델로 차례대로 호출하지 않고 풀 단위 중단 |
| timeout·종료 불명 | 실제 프로세스 종료 확인 전 슬롯 해제·중복 실행 금지 |

승격 시 전체 대화를 복사하지 않는다. 작업 지시, 허용 파일의 현재 상태, 실패한 완료 조건과 짧은 출력, 이미 시도한 접근만 전달한다. 원본 로그는 파일로 유지한다.

초기 제안은 일반 제한 편집의 전체 모델 호출을 최대 3회로 제한하는 것이다. Opus 중심 경로는 초기 시도와 필요한 수정 1회로 시작한다. 예산 한도는 역할별 시도 수와 별도로 작업 전체에 적용한다.

### 4.3 공유 풀 소진과 모델 오류 구분

현재 런타임은 프로필의 선택적 `pool` 연결과 구조화된 공급자 오류를 사용한다. 확인된 풀 소진이면 같은 풀에 속한 fallback 모델을 더 호출하지 않는다. 일반 모델 오류와 rate-limit은 풀 전체 소진으로 간주하지 않으며, 할당량 범위가 불명확하면 `unknown`으로 중단해 상위에 보고한다.

429 자체가 항상 풀 전체 소진이라는 뜻도 아니다. 요청 빈도 제한, 모델 서비스 제한, 계정·기간별 소진을 구분할 수 있는 공식 응답이 있을 때만 pool-exhausted로 기록한다. 응답이 불명확하면 unknown 상태로 중단·상위 보고하며 모델들을 순회해 소진 여부를 시험하지 않는다.

## 5. 할당량과 비용 기록 설계

### 5.1 지표를 분리한다

1. **모델 usage:** 공급자가 보고한 입력·출력·캐시·합계 토큰. 누락은 null이다.
2. **할당량 차감:** 동일 풀, 동일 창에서 측정한 잔여 퍼센트포인트 차이.
3. **금액:** 공급자에게 실제 제공받은 금액만 기록한다.
4. **완료 비용:** 재시도·승격·검토·통합을 포함한 전체 작업의 사용량과 시간.

0으로 보고된 추론 토큰은 내부 추론이 없었다는 증거가 아니다. 토큰 수를 금액이나 구독 차감량으로 임의 변환하지 않는다.

### 5.2 스냅샷 기록 형식

아래 형식은 조직 설정과 분리된 quota snapshot 레코드로 구현돼 있다. `quota-record`가 검증·저장하고, `quota-compare`가 같은 풀·계정·갱신 창인지와 다른 활동의 개입 여부를 확인한다.

```json
{
  "schemaVersion": 1,
  "poolId": "agy-shared",
  "accountProfile": "current",
  "observedAt": "2026-09-14T00:00:00.000Z",
  "source": "user-snapshot",
  "windows": [
    { "kind": "weekly", "remainingPercent": 95.84, "resetAt": null },
    { "kind": "five-hour", "remainingPercent": 92.32, "resetAt": null }
  ],
  "otherActivity": "unknown"
}
```

사용자 화면을 자동화된 공식 계측처럼 기록하지 않는다. 자동 수집은 실제 지원되는 CLI/API를 확인한 뒤 추가한다. 새 비공개 엔드포인트나 계정 파일 위치를 추측하지 않는다. 기존에 허용된 자동 수집 경로가 없으면 수동 전후 스냅샷을 받을 수 있지만, 일반 작업마다 사용자에게 할당량을 입력하라고 요구하지 않는다.

### 5.3 유효한 차감량 비교 조건

- 같은 계정·그룹·갱신 창의 전후 값이어야 한다.
- 중간 갱신이나 다른 세션 사용이 있으면 그 배치의 모델별 차감량은 판정 불가다.
- 표시 지연을 확인하고 안정된 값 또는 지연 가능성을 기록한다.
- 차이가 화면 해상도보다 작으면 0 비용이 아니라 측정 한계 이하로 기록한다.
- 비교용 호출은 순차 실행해 차감량 귀속을 확인한다. 실제 조직의 병렬 처리 성능은 별도 실험한다.
- 주간과 5시간 창 모두를 기록한다. 어느 한쪽이 부족하면 다른 쪽 여유만 보고 추가 병렬 실행하지 않는다.

초기 예산 정책은 전체 잔여량의 숫자를 모델 가격으로 해석하지 않고, 업무에 남겨둘 최소 여유와 새 실험에 쓸 수 있는 상한으로 사용한다. 구체적 상한은 실험 시작 전 확정한다.

## 6. 비교 실험과 후속 운영 검증

### 6.1 실험 단계

**E1: 모델별 기준선, 완료.** 여섯 대표 작업을 각 모델에 한 번씩 배정해 18회를 호출했다. 최초 입력·기준 커밋·수용 검사를 맞췄으며 자동 재시도는 하지 않았다. 이 결과는 작업 유형별 후보를 좁히는 탐색이며 통계적 우열 확정이 아니다.

**E2: 운영 경로 비교, 완료.** 동일한 대표 작업 묶음으로 opus-first와 balanced를 각각 6회 비교했다. 품질, 모델 호출 시간과 토큰을 기록했으며, 지원되는 전후 스냅샷이 없어 실제 할당량 차감은 판정 불가로 남겼다.

**E3: 실제 업무 확인, 후속 운영 검증.** 선정한 경로로 제한된 실제 작업을 수행할 때 통합·검토·사람 수정까지 집계해 fixture 실험의 결과가 유지되는지 확인한다. E3는 P0–P4 기능 구현의 완료 조건이 아니며, 반복 가능한 실제 업무 표본이 생길 때 별도 결과로 기록한다.

E1/E2 결과와 제한은 [모델 라우팅 결과](../../experiments/ROUTING_REPORT.md)에 기록돼 있다. E3나 반복 실험을 위한 추가 모델 호출은 해당 업무의 위임 범위와 호출 예산을 따른다.

### 6.2 대표 과제

| 유형 | 과제 예 | 평가할 차이 |
|---|---|---|
| 좁은 편집 | 경계값·형식·문서 위치 수정 | GPT-OSS 최초 성공과 추가 호출 비용 |
| 검색·인용 | 여러 파일에서 근거 수집 | 정확한 인용 비율과 미검증 인용 |
| 일반 구현 | 작은 기능과 오류 처리 | Sonnet과 Opus의 성공률·시간 |
| 다중 파일 변경 | 공개 인터페이스를 보존하는 리팩터링 | 계약 누락·범위 위반·통합 비용 |
| 회귀 검토 | 검사는 통과하지만 기존 경로가 깨진 변경 | 놓친 결함과 허위 지적 |
| 충돌·실패 복구 | 두 작업의 인터페이스 충돌 | 올바른 원인 분류와 재작업 총량 |

### 6.3 Orca worktree와 감독

- `orca-cli`와 `orchestration`의 현재 버전 가이드를 읽는다.
- 비교 후보마다 같은 기준 커밋의 독립 Orca child worktree를 사용한다.
- 다른 모델의 결과를 읽지 못하도록 과제 문맥을 분리한다.
- 실제 편집 과제와 JSON 결과 생성 과제를 별도 집계한다.
- 모델 배정·Task/Dispatch·worktree receipt·사용량·검사 결과를 기록한다. 비대화 하네스에 없는 Dispatch를 만들었다고 보고하지 않는다.
- 고정 수용 검사는 작업자가 바꾸지 못하는 위치에 두고 결과를 외부 검사기로 평가한다.
- 독립 비교 결과를 운영 코드에 자동 머지하지 않는다. E3 실제 업무 결과만 정상 검토·통합 경로로 전달한다.
- 종료가 확인된 실험 셸을 닫고, 증거는 보존한다. 정산되지 않은 감독 워커를 강제로 회수하지 않는다.

### 6.4 실행 순서와 중단 조건

- 할당량 비교에서는 모델 호출을 순차 실행하고 작업별 모델 순서를 회전한다. 항상 Opus를 마지막에 실행해 캐시·시간대 효과를 편향시키지 않는다.
- 캐시 사용량과 재사용 세션 여부를 기록한다. 새 세션 비교와 문맥이 누적된 세션 비교를 섞지 않는다.
- 우선 대표 작업 2개씩의 작은 배치로 진행한다. 잠정 예산은 배치당 초기 호출 6회와 명시된 복구 호출 상한이다.
- 제안하는 실험 중단 기준은 어느 한 창의 추가 차감이 5퍼센트포인트를 넘거나, 운영용 최소 여유를 침범하거나, 풀 소진/프로세스 종료 불명이 발생하는 경우다. 수치는 사용자 선택 및 E1 관측으로 조정할 실험 정책이며 공급자 제한이 아니다.
- 스냅샷 귀속이 불가능해지면 품질·토큰 기록은 유지하고 할당량 비교만 판정 불가로 남긴다. 불필요한 재호출로 숫자를 맞추지 않는다.

## 7. 비교 기준과 채택 조건

| 지표 | 계산 또는 판정 |
|---|---|
| 최초 성공률 | 첫 실행에서 고정 수용 조건을 통과한 과제 / 전체 과제 |
| 최종 성공률 | 허용된 전체 예산 내 완료 과제 / 전체 과제 |
| 놓친 결함 | 독립 검사·의미 검토에서 발견된 미해결 결함 |
| 완료까지 토큰 | 최초 호출 + 재시도 + 승격 + 필요한 검토·통합 호출 |
| 완료 시간 | 배정부터 최종 수용까지의 벽시계 시간; 모델 시간 합계도 별도 기록 |
| 할당량 / 완료 과제 | 귀속 가능한 창의 퍼센트포인트 차감 / 수용된 과제 수 |
| 사람 개입 | 사람이 수정·요구 보완·계정 복구한 횟수와 이유 |

의사결정 순서:

1. 미해결 중요 결함이나 수용 실패가 있으면 토큰 절약만으로 해당 경로를 채택하지 않는다.
2. 비슷한 품질에서 완료까지의 할당량·시간·사람 개입을 비교한다.
3. 실제 차감량이 미확인이면 토큰·시간만의 잠정 결론이라고 명시한다.
4. GPT-OSS가 유리한 유형만 유지하고 다른 유형은 Sonnet/Opus로 바로 배정한다.
5. 혼합 운영의 절약이 작거나 선택·승격의 복잡성으로 사라지면 opus-first를 유지한다.

잠정 채택 기준은 반복 비교에서 품질을 낮추지 않으면서 완료 시간 또는 귀속 가능한 할당량이 약 10% 이상 개선되는 경우다. 이는 운영 판단용 초기 기준이며 통계적 유의성을 뜻하지 않는다. 평균과 함께 개별 결과·실패·분산을 보존하고, 표본이 작으면 결론을 유보한다.

## 8. 보고 취합과 머지 비용 정책

- 하위가 성공할 때마다 Opus 세션을 깨워 전체 보고를 다시 요약하지 않는다.
- `aggregate`가 작업 누락·중복·실패·미해결 항목과 사용량을 결정적으로 취합한다.
- 정상 보고는 요약과 근거 위치만 올리고, 상위 모델은 실패·충돌·의미 판단이 필요한 부분을 읽는다.
- 동일 source/base/검사/환경의 성공 증거는 재사용한다.
- 통합 source가 달라지면 필수 검증을 새로 수행한다. 모델 변경 자체를 이유로 같은 기계적 검사를 무조건 반복하지 않는다.
- 최종 머지 전 상위가 정한 수용 검사와 evidence를 대조한다. 보고를 짧게 만든다는 이유로 필수 증거를 버리지 않는다.
- 같은 모델의 자기평가만으로 고위험 검토를 마치지 않는다. 필요한 독립 문맥과 객관적 검사 기준을 사용하되, 단순 변경까지 모델 3개에게 중복 검토시키지 않는다.

## 9. 구현 작업과 순서

### P0 — 현재 근거 보존: 이 계획에서 완료

- 사용자 제공 공유 그룹 화면과 해석 한계 기록.
- 기존 실험의 최초 성공과 완료까지 총량 분리.
- opus-first, balanced, 기존 GPT-OSS 우선 대조군 정의.
- 현재 구현과 제안 정책을 구분.

### P1 — 선택 가능한 모델 프리셋: 완료

- `examples/`에 opus-first와 balanced 예제를 추가한다.
- `org-setup`에서 최초 구성 시 프리셋을 제안하고 직급별 구독/모델을 확인한다.
- `org-edit`에서 프리셋 적용 전후와 바뀌는 프로필만 표시한다.
- 기존 조직 파일은 자동 변경하지 않는다. 새 작업만 변경된 revision을 사용한다.
- 실제 사용 가능한 모델 ID는 Agy에서 확인한다: `claude-opus-4-6-thinking`, `claude-sonnet-4-6`, `gpt-oss-120b-medium`.

### P2 — 풀 단위 할당량 인식: 완료

- 조직 스키마에 풀과 프로필의 명시적 연결을 설계하고 버전 호환 정책을 정한다.
- `providers.mjs`의 공급자 오류를 모델 오류, rate-limit, 확인된 풀 소진, unknown으로 분류한다.
- `worker.mjs`에서 같은 풀 소진의 fallback 연쇄를 차단한다.
- 자동 스냅샷 수집은 실제 지원되는 수단이 확인된 경우에만 추가한다.
- 만료된 스냅샷을 최신 잔여량처럼 사용하지 않는다.

### P3 — 사용량과 배정 근거 기록: 완료

- 작업에 requested/effective 모델, 선택 이유, 프리셋 revision, 승격 이유를 기록한다.
- usage와 할당량 스냅샷은 서로 다른 레코드로 보존한다.
- `aggregate`와 `org-show`에 완료까지 누적 사용량, 확인 가능한 풀 상태, 미확인 항목을 표시한다.
- API에서 실제 모델이 확인되지 않으면 requested만 기록하고 effective를 지어내지 않는다.

### P4 — 확대 실험과 프리셋 선택: 완료

- E1/E2 평가기와 과제 fixture를 추가한다.
- 기존 보고서와 새 실험 결과를 구분하고 결과를 재현 가능한 요약으로 내보낸다.
- 업무별 배정표를 확정하고 사용자가 선택한 조직에 `preset --apply` 또는 `org-edit`으로 적용할 수 있게 한다.
- E3 실제 업무 검증은 후속 운영 표본으로 분리한다.

## 11. 이번 변경의 경계

현재 구현은 프리셋 선택·공유 풀 인식·배정/사용량 기록을 제공하지만 기존 조직에 Opus나 balanced를 자동 적용하지 않는다. E1/E2 결과에 따라 balanced를 잠정 권고할 뿐이며, 기존 조직 설정은 사용자가 `preset --apply` 또는 `org-edit`을 실행할 때만 변경한다. E3와 반복 실험은 실제 업무의 위임 범위와 별도 호출 예산이 있을 때 진행한다.
