## 1. 배경과 제품 방향

Orca-Skills는 PM / PL / Senior / Junior / Intern 역할을 모델·계정과 분리하고, 실제 작업에 필요한 역할만 실행하는 에이전트 조직을 지향한다. 조직도에 더해 작업이 시작되고, 검토되고, 수용되는 공통 규칙을 갖추는 것이 이번 변화의 목적이다.

참고 글인 [The AI-Native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)은 개발 단계 사이를 기록된 산출물과 검증으로 연결하는 접근을 제안한다. 여기서는 그 방향을 Orca 조직에 맞게 적용한다. 아래 데이터 모델, 상태 전이, CLI 및 단계 구분은 Orca-Skills에 대한 자체 설계 제안이다.

목표 제품 경험:

> 사용자가 조직에 목표를 맡기면, PM이 완료 기준을 정리하고 필요한 역할을 배정한다. 작업자는 결과와 증거를 제출하고, 조직은 검토·통합·재작업을 수행한다. 사용자에게는 해결해야 할 실제 판단과 확인 가능한 최종 결과가 전달된다.

조직도는 책임과 위임 관계를 나타내고, 작업 그래프는 실행 순서와 의존성을 나타낸다. 두 구조를 동일하게 만들지 않는다. PM → PL → Senior → Junior → Intern을 매번 순차 실행하지 않는다.

## 2. 현재 기반과 부족한 연결

계획 수립 시 현재 작업 디렉터리를 읽은 결과이며, 실행 검증 결과가 아니다. 저장소가 변경 중이므로 구현 시작 시 인터페이스를 다시 확인한다.

| 영역 | 현재 근거 | 유지할 것 | 추가할 것 |
|---|---|---|---|
| 조직 구성 | `schemas/organization.schema.json`, `scripts/core.mjs`, `examples/organization.json` | 역할·모델 분리, revision, 동시 인원, 선택된 fallback | 업무 정책과 실행 조직 스냅샷 연결 |
| 작업 입력 | `scripts/worker.mjs`의 `validateTask`, `examples/task.json` | 파일 범위, 검사 argv, 환경, base, 위험도 | 목표·수용 기준·의존성·검토 요구 |
| 편집 실행 | `makePrompt`, `applyEdits`, `work` | JSON 편집, 원본 해시, 전체 응답 검사 후 적용 | 작업 계약 revision과 실행 결과 연결 |
| 검증 | `scripts/evidence.mjs` | HEAD·base·tree·검사·환경·원본 로그 대조 | 계약 변경과 의미 검토의 유효성 판정 |
| 머지 전 확인 | `teams-org.mjs`의 `merge-check --task` | 신뢰한 task의 검사·환경과 증거 비교 | 최종 통합 대상의 검토·수용 조건 확인 |
| 보고 취합 | `aggregate` | 누락·중복·실패·issues 차단, 취합과 승인 분리 | 문자열 검토 요구를 구조화된 gate로 전환 |
| 감독 실행 | PM/PL skill | Orca Run/Task/Dispatch, accepted settlement, 안전한 회수 | 업무 상태와 Orca 실행 ID 연결 |
| 비용·실험 | `experiments/`, 호출 기록 | 실제 usage와 미확인 비용 구분 | 조직 단위 품질·개입·시간 평가 |

현재 `work`는 검사 통과 시 `status: passed`를 기록하고, `risk !== low`이면 Senior 검토 필요 문장을 `issues`에 추가한다. `aggregate`는 issues가 있는 보고를 차단한다. 즉 검토 요구를 완전히 무시하는 상태는 아니지만, 검토 수행·반려·해결을 표현하는 구조화된 기록이 부족하다.

제한 편집 하네스와 일반 감독 작업은 서로 다른 실행 경로다. `work` 자체가 Orca Dispatch나 `worker_done`을 만들지는 않는다. 새 설계에서도 이 경계를 유지한다.

## 3. 적용 원칙

1. **결과의 계약을 먼저 정한다.** 작업자는 목표, 변경 범위, 완료 기준, 필요한 검토를 알고 시작한다.
2. **문서량을 작업 크기에 맞춘다.** 작은 변경은 task 하나로 충분하다. 큰 변경만 설계·공유 계약 문서를 연결한다.
3. **자동 검사 통과와 최종 수용을 분리한다.** 테스트 통과만으로 요구사항 충족, 검토 완료 또는 머지 권한을 선언하지 않는다.
4. **판단과 강제 조건을 분리한다.** 역할 skill은 판단 방법을 안내하고, 런타임은 상태·범위·증거 조건을 검사한다.
5. **기존 권한을 보존한다.** 이미 위임된 작업을 매번 재승인받지 않는다. 에이전트 내부 검수는 사용자의 외부 작업 권한을 대체하지 않는다.
6. **동일한 증거는 재사용한다.** 전제가 같을 때만 재사용하고, 변경 시 필요한 검토와 검사만 무효화한다.
7. **실패를 숨기지 않는다.** 소진·타임아웃·실행 상태 불명을 성공으로 바꾸지 않는다.
8. **Orca의 감독 기능을 재구현하지 않는다.** 스킬 패키지는 업무 계약과 gate를 담당하고, 실행 소유권·프로세스·회수는 Orca를 사용한다.
9. **조직의 효과를 실측한다.** 에이전트 수나 직급 수를 성과로 보지 않는다.

## 4. 목표 업무 흐름

```text
사용자 요청 / 기존 작업 기록
  → PM: 목표·수용 기준·위임 범위 정리
  → 작업 계약 확정
  → 필요할 때 PL: 분할·공유 계약·의존성 확정
  → 준비된 작업만 배정
  → 작업자: 구현 + 검사 증거 + 미해결 사항
  → 위험도에 맞는 의미 검토
  → 필요할 때 별도 worktree에서 통합·검증
  → PM: 원래 목표의 충족 여부 수용
  → 요청 범위의 결과 전달 / PR / 머지

실패 또는 반려
  → 원인 분류
  → 요구 보완 / 재분할 / 환경 복구 / 구현 수정
  → 새로운 revision 또는 attempt로 재개
  → 반복 가능한 교훈을 검사·skill·eval 후보로 기록
```

단일 저위험 작업에서는 PM과 Intern만 사용할 수 있다. 다중 작업일 때 PL을 활성화하고, 의미 판단이 필요할 때 Senior를 사용한다. 최종 수용을 위해 새로운 PM 모델 세션을 매번 만들지 않고 기존 감독 세션과 결정적 집계를 활용한다.

## 5. 역할별 책임과 산출물

| 역할 | 주 책임 | 입력 | 산출물 | 책임 경계 |
|---|---|---|---|---|
| PM | 사용자 목표와 최종 결과 책임 | 요청, 기존 맥락, 위임 범위 | 목표·수용 기준, 최종 수용 결정 | 사용자 위임 밖의 머지·배포·발송을 스스로 허가하지 않음 |
| PL | 분할·의존성·통합 | 작업 계약, 조직 스냅샷 | 작업 그래프, 배정, 통합 결과 | 하위 성공 보고만으로 통합 성공 판정하지 않음 |
| Senior | 의미 검토와 어려운 판단 | 계약, diff, 실행 증거 | 기준별 검토 결과, 수정 요구 | 검토만 맡았으면 구현자에게 수정을 반환 |
| Junior | 기능 구현과 제한 작업 통합 | 할당된 계약·공유 인터페이스 | 구현 결과, 검사 증거, 미해결 사항 | 수용 기준을 임의로 약화하지 않음 |
| Intern | 제한 편집·인용·초안 | 허용 파일, 좁은 지시 | JSON 편집 또는 확인 가능한 인용 | 결과 수용·검토 면제·권한 확대를 선언하지 않음 |

Senior가 에이전트인 경우 결과는 `agent-review`다. 사람의 승인으로 기록하지 않는다. 독립 검토가 요구되면 구현 Dispatch와 다른 검토 Dispatch를 사용한다. 컨텍스트 분리는 오류 독립성을 보장하지 않으므로 수용 기준과 실제 실행 증거도 함께 확인한다.

## 6. 데이터 계약 제안

### 6.1 작업 계약 v2

`task.schema.json`과 정규화 함수를 추가한다. 기존 제한 편집 필드를 유지하면서 조직 업무 필드를 추가한다. 다음 예시는 목표 형식이며 현재 CLI에서 지원한다고 가정하지 않는다.

```json
{
  "schemaVersion": 2,
  "id": "fix-expiry-boundary",
  "revision": 1,
  "kind": "edit",
  "goal": "만료 시각과 현재 시각이 같으면 만료된 것으로 처리한다.",
  "instruction": "src/expiry.mjs의 경계 비교를 수정한다.",
  "nonGoals": ["공개 API 변경", "시간대 정책 변경"],
  "constraints": ["기존 호출자와 호환성을 유지한다."],
  "files": ["src/expiry.mjs"],
  "checks": [["node", "--test", "tests/expiry.test.mjs"]],
  "acceptance": [
    {"id": "expiry-boundary", "description": "직전·동일·직후 시각의 동작이 맞다.", "method": "check", "checkIndexes": [0]},
    {"id": "public-api", "description": "공개 함수 시그니처가 유지된다.", "method": "review"}
  ],
  "dependencies": [],
  "contractRefs": [],
  "openQuestions": [],
  "risk": "normal",
  "reviewRequirements": [{"id": "semantic-review", "kind": "agent-review", "role": "senior", "criteria": ["public-api"]}],
  "environment": "node22-lockfile-and-fixtures-revision-1",
  "baseRef": "origin/main"
}
```

설계 규칙:

- 기준 ID는 작업 내에서 유일해야 한다. `checkIndexes`는 실제 `checks` 항목을 참조해야 한다.
- 검사 항목과 수용 기준의 연결은 설명이다. 검사 통과가 모든 제품 요구를 증명한다고 자동 해석하지 않는다.
- `dependencies`는 task ID와 요구 revision 또는 수용된 결과 식별자를 참조한다. 존재하지 않는 의존성과 순환을 거부한다.
- `contractRefs`는 경로와 commit/hash를 함께 고정한다. 같은 파일을 수정하지 않아도 공유 API 계약이 다르면 재검토한다.
- 실행을 막는 질문과 참고 질문을 구분한다. 필수 질문이 미해결이면 `ready`로 전환하지 않는다.
- `files`는 수정 허용 범위다. 읽기 문맥이 더 필요하면 별도 `contextRefs`를 설계하되 편집 권한을 확대하지 않는다.
- 대화·토큰·비밀값을 계약에 복사하지 않고 필요한 기록 위치를 참조한다.
- 계약 수정은 revision을 올린다. 기존 실행 기록을 덮어쓰지 않는다.

### 6.2 실행 경로별 작업 종류

첫 단계의 v2는 `kind: edit`만 제한 편집 하네스에서 실행한다. 탐색·설계 작업에 가짜 수정 파일과 의미 없는 검사 명령을 요구하지 않는다.

후속 단계에서 `research`, `design`, `integration`을 별도 discriminated schema로 추가한다. 이들은 Orca 감독 실행 경로를 사용하고, 파일 편집 대신 인용·설계 결정·통합 결과 등 각 종류에 맞는 증거를 요구한다. `work`는 지원하지 않는 kind를 명확히 거부한다.

### 6.3 실행 및 검토 기록

구조화된 기록에는 다음 필드를 포함한다.

| 기록 | 필수 정보 |
|---|---|
| 실행 | task ID/revision/hash, 조직 revision/hash, attempt ID, 실행 경로, Orca ID 또는 하네스 run ID |
| 구현 결과 | 수정 파일, source fingerprint, 검사 evidence 참조, 실패·미해결 항목 |
| 검토 | review ID, 요구 gate ID, 검토자 종류·실행 ID, 대상 task hash/source fingerprint, 기준별 결론, findings |
| 수용 | decision ID, 대상 결과 집합, 충족한 기준, 근거, 판단자, 범위 |
| 재작업 | 원인 유형, 증거, 다음 소유자, 원래 attempt, 소모한 예산 |

검토 결론은 `approved`, `changes-requested`, `inconclusive`로 제한한다. 필수 기준이 누락되거나 결론이 불명확하면 해당 gate를 통과하지 않는다.

finding은 고유 ID와 `open`, `resolved`, `accepted-risk` 상태를 갖는다. 삭제로 해결 처리하지 않는다. `accepted-risk`는 해당 종류의 위험 수용 권한이 있는 주체와 이유가 필요하며, 필수 검사 실패를 위험 수용으로 통과시키지 않는다.

### 6.4 권한 기록

업무 계약의 `risk`나 PM 역할 자체는 외부 작업 권한이 아니다. 실행 스냅샷에 기존 사용자 지시 또는 설정에서 확인한 위임 범위를 참조한다.

- 내부 구현·검토·재분할: 기존 요청과 조직 정책 범위에서 자율 실행.
- PR·머지·배포·외부 발송: 해당 동작에 대한 기존 위임을 확인하고 없으면 실제 필요 시 요청.
- 권한이 이미 있으면 같은 내용을 재질문하지 않는다.
- 모델이 생성한 `approved: true`나 환경변수만으로 사용자 승인을 만들지 않는다.
- 로컬 기록의 해시는 무결성 대조 수단이다. 악의적 작성자에 대한 인증을 제공한다고 표현하지 않는다.

## 7. 상태 전이와 gate

### 7.1 상태는 역할 이름과 분리한다

업무 상태: `draft → ready → running → submitted → accepted`.

예외 상태: `blocked`, `failed`, `cancelled`. 재작업은 이전 결과를 보존한 새 attempt로 수행한다. 소유권과 프로세스 생존 여부는 별도 실행 상태로 유지한다.

검토·통합은 단일 상태 문자열에 전부 압축하지 않고 다음 gate 묶음으로 표현한다.

| gate | 통과 조건 | 판정 담당 |
|---|---|---|
| contract-ready | 유효한 계약, 필수 질문 해결, 필요한 입력 고정 | PM/PL 판단 + 런타임 검사 |
| dependencies-ready | 필요한 선행 결과가 지정 revision으로 수용됨 | 런타임 |
| checks-passed | 신뢰한 계약의 검사와 환경에 맞는 실제 증거 | 기존 verify/validateEvidence |
| review-complete | 필수 검토와 기준별 결론 충족, 열린 차단 finding 없음 | 검토 담당 + 런타임 |
| integration-passed | 최종 통합 소스에 대한 프로젝트 검사 충족 | PL + 검증 런타임 |
| outcome-accepted | 사용자 목표의 필수 수용 기준 충족 | PM |

해당하지 않는 gate는 정책에 따른 `not-required`와 이유를 기록한다. 작업자가 임의로 생략할 수 없다. PM의 목표 판단을 단순 필드 존재 검사로 대체하지 않으며 런타임은 필수 증거의 누락을 막는다.

### 7.2 무효화 규칙

- 코드·HEAD·base·검사·환경 변경: 기존 검증 재사용 규칙에 따라 무효화.
- 수용 기준·제약·검토 요구 변경: 계약 revision 증가, 수용과 관련 의미 검토 무효화.
- 공유 계약 변경: 의존 작업을 영향 검토 대상으로 표시하고 필요 시 재배정.
- 조직 설정 변경: 진행 중인 실행은 시작 당시 스냅샷 유지. 새 정책을 적용하려면 명시적으로 새 실행을 준비.
- 조직 skill 버전 변경: 새 실행부터 적용. eval로 회귀 확인하고 기존 실행에 소급해 성공을 선언하지 않음.
- 검토한 source와 최종 통합 source가 다르면 그대로 재사용하지 않는다. v1 구현에서는 보수적으로 재검토하고, 정밀한 영향 분석은 후속 최적화로 둔다.

### 7.3 Orca 실행 상태와의 관계

Orca의 accepted settlement는 워커 실행 결과와 소유권 처리에 관한 사실이다. 제품 요구 충족을 의미하는 `outcome-accepted`와 동일시하지 않는다.

- 실제 Run/Task/Dispatch/worktree ID를 저장한다. 없는 ID를 임의 생성하지 않는다.
- 하네스 run은 Dispatch 없이도 존재할 수 있다. 감독자와 연결될 때만 실제 Dispatch를 기록한다.
- timeout은 업무 성공도 프로세스 종료 증거도 아니다.
- 중복 완료 이벤트는 event ID와 attempt ID로 중복 제거한다.
- 오래된 attempt의 결과가 새 attempt를 완료시키지 못하게 한다.

## 8. 기록 저장과 중단 복구

기존 `.orca/runs`, `.orca/evidence`, `.orca/worktrees` 경로를 보존하고 새 업무 기록을 추가한다.

```text
.orca/
  workflows/<workflow-id>/
    request.json
    organization.json
    tasks/<task-id>/revisions/<revision>.json
    reviews/<review-id>.json
    decisions/<decision-id>.json
    events/<event-id>.json
    state.json
  runs/<run-id>/...
  evidence/...
  worktrees/...
```

- request에는 목표와 위임의 최소 기록만 저장한다. 필요 이상의 대화 전문을 보관하지 않는다.
- revision, review, decision은 새 파일로 기록하고 기존 파일을 덮어쓰지 않는다.
- `state.json`은 이벤트에서 재구성할 수 있는 조회용 상태다.
- 상태 변경에 expected revision과 잠금/원자적 쓰기를 적용한다. 두 감독자가 같은 전이를 동시에 확정하지 못하게 한다.
- 파일 기반 첫 구현은 한 coordinator 소유권 아래에서 실행한다. 다중 호스트 공유 파일시스템을 지원한다고 가정하지 않는다.
- 외부 Orca 작업 호출 전에 작업 의도를 기록하고 반환 receipt를 저장한다. 호출 성공 후 기록 전 중단되면 재생성 전에 실제 Orca 상태를 조회해 대조한다.
- 상태가 불명확하면 `blocked`로 남기고 중복 워커를 자동 생성하지 않는다.
- `.orca`는 계속 Git 제외한다. 공유해야 할 결정·교훈은 비밀과 로컬 경로를 제거한 요약으로 명시적으로 내보낸다.
- Git 제외 로그를 영구 조직 기억으로 간주하지 않는다. 로컬 실행 기록과 버전 관리할 지식의 목적을 구분한다.

## 9. 실패 처리와 조직 기억

### 9.1 실패 유형에 따른 라우팅

| 유형 | 예시 | 다음 담당/처리 |
|---|---|---|
| requirement-ambiguity | 기대 동작이 서로 모순 | PM이 계약 보완 |
| scope-too-large | 문맥·파일 범위 초과 | PL이 재분할 |
| implementation-error | 재현 가능한 동작 실패 | 작업자 수정, 필요 시 Senior |
| environment-failure | DB fixture 누락, 도구 실행 실패 | 환경 복구 작업으로 분리 |
| contract-conflict | API 형태 또는 데이터 계약 충돌 | PL과 관련 설계 담당이 계약 조정 |
| review-rejection | 수용 기준 누락, 위험한 설계 | finding을 연결해 원 소유자에게 반환 |
| quota-exhausted | 구독 한도 도달 | 저장된 fallback/stop 정책 |
| process-unknown | timeout 후 종료 확인 불가 | 실행 상태 대조 후 회수 또는 재개 |

종료 코드·timeout·quota 등 결정적 신호를 우선한다. 모델이 원인을 분류하면 근거와 불확실성을 함께 남긴다. 분류 자체가 불확실하면 강한 모델로 계속 재시도하지 않고 감독자에게 반환한다.

attempt를 새로 만들어도 workflow 전체 예산을 초기화하지 않는다. 호출 수·시간·재작업 횟수 한도를 합산하고, 확인 가능한 usage만 집계한다. USD 비용과 구독 차감량이 제공되지 않으면 `unknown`으로 유지한다.

### 9.2 교훈을 반영하는 경로

실패 해결 후 lesson 후보를 만들되 자동으로 모든 skill을 수정하지 않는다.

| 교훈 성격 | 반영 위치 |
|---|---|
| 결정적으로 확인 가능한 규칙 | 검사·린터·런타임 조건 |
| 특정 작업의 반복 절차 | 해당 역할 또는 작업 skill |
| 저장소 고유 지식 | 대상 저장소 지침 |
| 설계 선택 이유 | 버전 관리하는 설계 결정 기록 |
| 에이전트 행동 회귀 | 조직 eval 시나리오 |

lesson에는 실패 근거, 변경 후보, 담당자, 재현 방법을 넣는다. 변경은 기존 리뷰 경로를 거치고 eval 결과와 연결한다. 동일한 내용의 후보를 묶고 더 이상 유효하지 않은 지침을 제거할 수 있어야 한다.

## 10. 구현 단계와 파일별 작업

아래 CLI 이름과 신규 파일명은 제안이다. 현재 지원되는 명령처럼 문서화하지 말고, 구현 PR에서 help·예제·skill을 동시에 갱신한다.

### P0 — 기준선과 호환성 고정

- 현재 `npm test` 결과를 기준선으로 기록한다.
- 진행 중인 저장소 변경과 새 계획의 변경 범위를 구분한다.
- task v1, 조직 v1, report/evidence v1의 실제 사용 경로를 확인한다.
- 제한 편집과 감독 실행의 공통 결과 계약을 설계한다.
- 현재 PL 예시 등에서 `merge-check --task`와 CLI가 일치하는지 정리한다.

완료 기준: 기존 동작 목록, 호환성 정책, 새 schema와 상태 전이 초안에 모순이 없다.

### P1 — 작업 계약 v2

- 신규: `schemas/task.schema.json`, `scripts/contracts.mjs`, v2 작업 예제.
- 수정: `worker.mjs`의 입력 검증·프롬프트 구성, `teams-org.mjs`의 prepare/work/verify.
- task hash와 revision을 snapshot과 report에 기록한다.
- 수용 기준, 제약, 필요한 문맥을 제한된 프롬프트에 포함한다.
- `prepare`에서 기존 base 고정과 함께 계약 스냅샷을 고정한다.
- 모델 출력은 편집 프로토콜에만 적용하고 계약 필드 변경은 받지 않는다.

완료 기준: v2 제한 편집이 기존 경로로 실행 가능하고, v1 사용자는 명시된 호환 경로를 계속 사용할 수 있다.

### P2 — 구조화된 검토와 수용 gate

- 신규: `schemas/review.schema.json`, `scripts/gates.mjs`.
- 수정: `evidence.mjs`, `worker.mjs`, `teams-org.mjs`.
- report에 구현·검사 결과와 미완료 gate를 분리한다.
- `review-record`, `gate-check`, `accept` 같은 명령을 추가한다.
- `aggregate`는 구조화된 gate를 집계하되 실제 source 대조를 대신하지 않는다.
- 문자열 Senior 요구는 구버전 입력으로만 처리하고 근거 없이 자동 해결하지 않는다.
- `merge-check`에 필요한 최종 검토 조건을 연결하되 사용자 권한·remote CI 확인은 별도 유지한다.

완료 기준: 검사 통과 상태에서 검토를 건너뛸 수 없고, 코드나 계약 변경 시 이전 검토가 무효화된다.

### P3 — 역할 지침 연결과 대표 흐름 완성

- PM: 목표·수용 기준 작성, 작은 작업 경로, 최종 수용, 위임 확인.
- PL: 공유 계약과 의존성, 결과 집합, 별도 통합 source 검증.
- Senior: 기준별 검토, source에 연결된 결론, finding 해결.
- Junior/Intern: 계약 준수, 수용 기준 변경 금지, 실패 반환 형식.
- org-show: 단순 passed 대신 현재 차단 gate·다음 담당·증거 위치 표시.
- org-setup/org-edit: 추가 정책은 필요한 기본값으로 시작하고 구독·모델을 다시 묻지 않음.

완료 기준: 단일 변경과 두 작업 통합 시나리오를 역할 지침만 따라 일관되게 수행할 수 있다.

**첫 출시 범위는 P0–P3로 제한한다.** 운영 알림 자동화와 완전한 자율 스케줄러 없이도 작업 계약 → 구현 → 검토 → 수용의 연결을 제공한다.

### P4 — 의존성 스케줄링과 복구

- 신규: `scripts/workflow.mjs`, workflow schema 및 상태 저장 모듈.
- 제안 명령: `workflow-create`, `workflow-status`, `workflow-resume`.
- 준비된 작업만 Orca 감독 실행에 배정한다.
- 작업 실행 ID·receipt를 저장하고 재시작 시 실제 Orca 상태와 대조한다.
- 중복 이벤트, 오래된 attempt, 동시 상태 갱신을 처리한다.
- 공유 인터페이스가 충돌하면 병렬 실행을 제한한다.
- 역할 concurrency뿐 아니라 진행 중 작업·리뷰 대기를 제한한다.

완료 기준: 중간에 감독자가 중단돼도 이미 실행된 일을 중복 시작하지 않고 복구한다.

### P5 — 실패 라우팅과 조직 eval

- 실패 분류·재작업 연결·workflow 전체 예산을 구현한다.
- `evals/organization/`에 대표 시나리오와 독립 평가기를 추가한다.
- 무료 로컬 회귀 검사와 실제 모델 실험 명령을 분리한다.
- lesson 후보와 검증된 지식 반영 흐름을 추가한다.

완료 기준: 단일 에이전트 대비 조직 경로의 품질·개입·비용을 재현 가능한 방식으로 비교할 수 있다.

### P6 — 선택적 운영 피드백

- 이슈·알림을 새 작업 후보로 받는 어댑터를 추가한다.
- 사건 중복 제거, 실행 한도, 중단 스위치, 결과 관찰 기간을 갖춘다.
- 첫 범위는 진단과 수정 제안까지다. 실제 배포·롤백은 별도 위임과 실행 경계가 준비된 환경에만 연결한다.

완료 기준: 같은 사건의 반복 입력이 중복 작업을 만들지 않고, 진전 없는 루프가 예산 내에서 멈춘다.

의존 순서: P0 → P1 → P2 → P3 → P4 → P5 → P6. eval 시나리오 정의는 P1부터 시작해 각 단계에서 검증한다.

## 11. 호환성과 이전 정책

- 기존 task v1은 기존 제한 편집 경로에서 지원한다. 새 요구 필드가 없다고 기존 명령을 갑자기 중단하지 않는다.
- 내부 정규화 시 v1 검사 기준을 가져올 수 있지만, 없던 제품 목표나 의미 검토 완료를 만들어내지 않는다.
- v1 보고는 기존 집계가 가능하다. 새 workflow 수용에 포함하려면 계약과 검토를 명시적으로 연결한다.
- evidence v1은 기존 기계적 검사의 증거로 재사용할 수 있다. 의미 검토와 최종 수용의 증거로 자동 승격하지 않는다.
- 조직 정책 확장이 schema 변경을 요구하면 명시적 migration과 revision 증가를 사용한다. 기존 사용자 설정을 자동 덮어쓰지 않는다.
- 각 실행에 plugin/skill 버전 또는 콘텐츠 hash를 고정한다. 설치 변경이 진행 중인 실행의 규칙을 바꾸지 않게 한다.
- 배포 설치나 사용자 구독 설정 변경은 구현 PR과 분리하고 기존 설치 경로를 따른다.

## 12. 검증 계획

### 12.1 로컬 결정적 테스트

기존 `tests/runtime.test.mjs`를 보존하고 계약·gate·workflow 단위로 의미 있는 실패 시나리오를 추가한다.

| 시나리오 | 기대 결과 |
|---|---|
| v1 task 입력 | 기존 제한 편집 경로 유지 |
| 잘못된 기준 참조·중복 ID·순환 의존성 | 실행 전 거부 |
| 작업자가 검사나 계약을 약화한 출력 | 계약 유지, 부적절한 변경 거부 |
| 테스트 통과, 필수 검토 없음 | submitted 유지, accepted 불가 |
| 같은 구현 Dispatch가 독립 검토 요구 충족 시도 | 거부 |
| 검토 후 소스·계약·base 변경 | 해당 gate 무효화 |
| 선행 결과 revision 불일치 | 후속 작업 배정 차단 |
| 모든 하위 검사 통과, 통합 검사 실패 | 전체 작업 미수용 |
| finding 삭제 또는 근거 없는 해결 | 검토 완료로 인정하지 않음 |
| accepted settlement 수신, 업무 gate 미완료 | 실행 정산과 업무 수용 분리 |
| 동일 이벤트 중복·늦은 attempt 완료 | 새 실행 상태 오염 없음 |
| 두 감독자의 동시 전이 | 하나만 확정, 나머지는 최신 상태 재조회 |
| timeout 후 프로세스 상태 불명 | 슬롯 유지, 중복 실행 차단 |
| retry/fallback 반복 | workflow 전체 예산 초과 불가 |
| 모델 비용 미제공 | 0원으로 추정하지 않고 unknown 표시 |

### 12.2 조직 행동 eval

초기에는 6개 시나리오로 시작한다.

1. 좁은 경계값 버그: 불필요한 역할 활성화 없이 해결.
2. 두 파일의 독립 수정: 병렬 결과를 통합하고 최종 검증.
3. 서로 다른 파일의 공유 API 충돌: 계약 의존성을 인식해 조정.
4. 구현은 통과하지만 요구사항 일부 누락: 검토에서 발견하고 재작업.
5. 모호한 요구와 환경 실패: 원인을 구분해 적절한 담당으로 반환.
6. 중단·재개와 지연 완료: 중복 작업 없이 기존 결과를 이어받음.

평가기는 모델의 완료 설명 대신 사전에 정의한 결과·소스·이벤트·검사 로그를 확인한다. 고정 평가 테스트는 구현자가 수정할 수 없는 위치에서 실행한다. 설계 판단은 별도 기준표로 검토하고 불확실한 판정을 분리한다.

실제 모델 비교는 같은 기준 저장소와 수용 기준에서 단일 실행 경로와 조직 경로를 비교한다. 요청·실제 모델, skill 버전, 캐시 조건, 실행 순서와 재시도를 기록한다. 반복 측정 없이 일반적 우열을 선언하지 않는다.

### 12.3 성과 지표

- 수용 기준 충족률과 놓친 결함.
- 요청부터 최종 수용까지의 벽시계 시간.
- 사람 개입 횟수·시간·이유.
- 리뷰 대기 시간과 재작업 횟수.
- 전체 모델 호출·실측 usage·확인 가능한 비용.
- 통합 실패, 중복 실행, 잘못된 성공 선언 건수.
- 실패가 회귀 eval 또는 재사용 지식으로 반영되기까지의 시간.

안전한 상태 처리에 관한 로컬 실패 시나리오는 모두 통과해야 한다. 성과 목표치는 기준선 측정 후 작업 유형별로 정한다. 초기 표본으로 일괄적인 속도 향상 수치를 약속하지 않는다.
