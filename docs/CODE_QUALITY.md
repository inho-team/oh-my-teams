# 코드와 스킬 검증

3.x는 실행기를 직접 구현하지 않는 스킬 패키지다. `npm run quality`는 활성 스킬의 이름과 설명을 검사하고, 설치되는 모든 Markdown 문서에서 제거된 런타임 명령 참조와 로컬 링크를 검사한다. 설치 문서는 실행 지침이므로 폐기 명령은 코드 블록이나 인용에도 넣지 않는다. 역사 설명은 설치되지 않는 저장소 문서에 둔다. 링크 대상은 플러그인 내부에 존재해야 하며, 저장소에만 있는 파일이나 플러그인 밖으로 연결되는 심볼릭 링크에 의존하면 실패한다. 공통 규칙은 설치에 포함되는 `plugins/oh-my-teams/references/`에 둔다.

두 호스트의 JSON 매니페스트가 현재 패키지의 고정 스킬 집합과 같은 디렉터리를 가리키는지 확인한다. Claude의 기본 `skills/` 탐색은 유지하며, 경로를 명시한다면 단일 경로나 배열 모두 검사하고 빈 배열은 거부한다. Codex의 `skills`는 설치에 포함된 디렉터리를 가리키는 문자열이어야 한다. 이는 OMT 패키지 계약의 검사이며 호스트의 전체 매니페스트 스키마를 대신하지 않는다.

메타데이터 문법은 [yaml](https://github.com/eemeli/yaml), 문서 링크는 [mdast-util-from-markdown](https://github.com/syntax-tree/mdast-util-from-markdown)으로 읽는다. 문법 오류, 중복 YAML 키와 문자열이 아닌 필수 필드를 거부하고, 정상적인 따옴표와 여러 줄 설명은 허용한다. Markdown의 인라인·참조형 링크와 이미지를 검사하며 코드 예제와 이스케이프된 문장은 링크로 취급하지 않는다. URL로 인코딩된 로컬 경로도 파일 경로로 확인한다. JavaScript 소스 검사는 [Acorn](https://github.com/acornjs/acorn/tree/master/acorn)의 구문 트리와 주석 위치를 사용한다. 파서는 모두 개발 의존성이며 플러그인 실행 의존성으로 배포하지 않는다.

메타데이터 영역은 `skills/<이름>/SKILL.md`에서만 제외한다. 참조 문서가 같은 파일 이름을 쓰거나 `---` 구분선으로 시작하더라도 본문 링크를 검사한다. 플러그인 경로 누락과 파일 읽기 등의 파일 시스템 오류는 경로와 오류 코드를 포함한 실패 보고서로 반환하며, 잘못된 파일 형식도 실패로 보고한다. 예상하지 못한 프로그래밍 오류는 파일 시스템 오류로 바꾸지 않는다.

`npm run sync:check`는 매니페스트의 버전이 `package.json`과 같은지 검사한다. `npm test`는 플러그인 폴더만 OS 임시 디렉터리에 복사해 설치 구조를 검사하며, 외부 파일 참조와 누락된 참조 문서를 거부하는지 확인한다. Windows 줄바꿈에서도 스킬 메타데이터를 읽을 수 있는지 검사하고, 필수 역할 런타임과 번들 provider가 다시 들어오지 않았는지도 확인한다. 이 검사는 실제 Orca 실행이나 에이전트의 지침 준수를 보증하지 않는다.

CI 상태 구분, 재개와 삭제 응답 단절에 대한 지침 검토에는 [실패 대응 시나리오](SCENARIO_CHECKS.md)를 사용한다. 실제 호스트 검증 결과와 문서 대조를 구분해 기록한다.

로컬 Markdown 링크의 조각 식별자는 대상 문서의 제목과 HTML 앵커에도 존재해야 한다. 제목은 [github-slugger](https://github.com/Flet/github-slugger)의 GitHub 규칙을 사용하며 한글·중복 제목·인라인 서식을 처리한다. 명시적인 HTML `id`와 `a`의 `name`은 [parse5](https://github.com/inikulin/parse5)로 읽는다. 코드 예제의 가짜 제목이나 HTML은 앵커로 세지 않는다. 파일 경로와 조각은 각각 URL 디코딩하며, 외부 URL과 Markdown 이외 파일의 조각은 검사하지 않는다. 정의되지 않은 참조형 문구는 Markdown 파서가 일반 텍스트로 취급하므로 링크 오류로 추정하지 않는다.

활성 `.mjs` 파일은 모듈 JSDoc을 작성하고 공개 export에는 인접 JSDoc을 붙인다. 공개 함수는 인자의 `@param`과 반환값의 `@returns`를 작성한다. `npm run quality`가 이 규칙과 실행문 180자 제한, core·어댑터·진입점의 의존성 방향과 순환 참조를 검사한다. 포맷은 Prettier가 결정한다. 새 클론에서는 `npm ci`를 실행한 뒤 `npm run format`, `npm run sync`, `npm run lint`, `npm test`를 차례로 실행한다. Jenkins의 정확한 실행 범위는 아래 표를 따른다.

Jenkins의 macOS checkout에는 [Git의 프로세스별 설정](https://git-scm.com/docs/git-config#ENVIRONMENT)을 사용하며 전역 설정 파일을 변경하지 않는다. 회귀 검사는 Jenkins에 선언한 환경 옵션을 실제 Git 프로세스에 적용해 값이 덮어써지는지, 빌드 밖의 값과 임시 전역 설정 파일은 그대로인지 확인한다.

검증하지 않은 Orca 세션이나 워크트리를 종료됐다고 가정하지 않는다. 삭제 전에 정확한 Orca ID, 소유 세션의 종료, Git 상태와 결과 전달을 다시 확인한다. 이 규칙의 정본은 [세션 소유권 구조](ARCHITECTURE.md)다.

개발 도구의 모듈 경계와 실행 가능한 공통 함수 예제는 [개발 도구와 공통 예제](DEVELOPMENT.md)를 따른다. 버전 동기화는 격리된 저장소에서도 검사하며, 누락되거나 형식이 잘못된 Codex 버전을 보고하고 복구한다.

## 검사 범위와 한계

| 검사 | 확인하는 범위 | 확인하지 않는 범위 |
|---|---|---|
| `quality`: 스킬 | 고정된 7개 스킬 집합과 YAML 메타데이터를 확인한다. | 실제 에이전트의 지침 준수는 검사하지 않는다. |
| `quality`: 설치 문서 | 설치되는 모든 일반 Markdown 파일의 폐기 명령 패턴, 링크·이미지·참조 정의, 로컬 대상의 존재와 플러그인 경계를 확인한다. Markdown 조각은 제목·HTML 앵커와 대조한다. | 외부 URL의 응답과 정의가 없어 일반 텍스트가 된 참조형 문구는 검사하지 않는다. 디렉터리 링크를 따라 전체 문서를 탐색하지 않는다. |
| `quality`: 저장소 문서 · `docs:check` | README·`docs/`·`evals/`의 일반 Markdown 파일에서 링크·앵커와 저장소 경계를 검사한다. `docs/todo/`도 포함한다. | 저장소 밖 대상, 외부 URL 응답과 폐기 명령의 역사적 언급은 검사하지 않는다. 설치 문서 경계를 바꾸지 않는다. |
| `quality`: 소스 | 활성 `.mjs`의 문법, JSDoc 태그, 주석을 제외한 줄 길이, 정적 import와 계층·순환 관계를 확인한다. 스코프 분석으로 공개 함수 별칭과 금지된 전역 참조도 확인한다. | 주석의 정확성, 모든 동적 호출과 런타임 동작은 보장하지 않는다. |
| `format:check` | Prettier로 `.mjs`, `.json`과 `.yaml` 형식을 확인한다. | Markdown의 문체와 표·링크는 대상이 아니다. |
| 내부 문서 검사 | 제한된 YAML과 JSON Schema, 요청·결과 대응, 관측·검토·전달·정리의 의미 규칙을 검사한다. `npm test`에서 설치 예제와 CLI·HTML 회귀 검사를 실행한다. | 실제 근거의 존재와 실행 식별자의 진위, 사용자 권한이나 호스트의 지침 준수는 증명하지 않는다. YAML 안의 임의 경로를 일반 링크로 탐색하지 않는다. |
| `sync:check` | 빌드 메타데이터 없는 엄격한 SemVer 정본, 세 매니페스트의 버전 일치, Codex 기본 버전과 14자리 UTC 달력 날짜를 확인한다. 윤년과 연도·시·분·초 범위도 검사한다. | 빌드의 출처나 실제 생성 시각은 증명하지 않는다. |
| `test` | 설치 복사본, 입력 오류, 포트 실패 주입, 동기화 복구, 실제 자식 프로세스 중단 후 재실행, 소스 규칙과 CI Git 설정을 검증한다. | 전원 장애, 실제 호스트 설치, 모델 행동, Orca 재개·회수와 Colima 실행은 자동 검증하지 않는다. |
| `verify` · Jenkins Linux·macOS | 로컬과 CI 모두 `lint` 뒤 `test`를 실행한다. CI는 먼저 `npm ci`를 실행한다. `lint`에 `quality`, `format:check`, `sync:check`가 포함된다. | 로컬 Windows 결과로 두 CI 단계의 성공을 대신할 수 없다. |

`passed`는 수행한 검사에서 진단이 없었다는 뜻이다. 호스트의 전체 스키마, 모든 배포 파일의 안전성이나 에이전트의 정상 동작을 보장한다는 뜻이 아니다. 설치 경계의 `realpath` 검사는 검사 시점의 경로를 확인하며, 이후 다른 프로세스가 경로를 바꾸는 상황까지 격리하지 않는다.

실제 코드로 재현한 공백과 수정 우선순위는 [프로젝트 분석](PROJECT_ANALYSIS.md)에 있다. 새 검사를 추가할 때에는 이 표의 범위도 함께 바꾼다.

별도 실행으로 확보한 [호스트 판단 평가](../evals/README.md)와 [실제 스킬 선택·Orca 재조회 검증](../evals/LIVE_INTEGRATION.md)은 `npm test`에 포함되지 않는다. 제공된 관측에 대한 판단, 실제 도구 호출과 검증하지 않은 장애 범위를 각각 구분해 기록한다.

JavaScript 어댑터는 Acorn의 구문 트리와 함께 `eslint-scope`의 바인딩·전역 참조 정보를 사용한다. 지역 인자나 객체 속성의 이름이 `Date`라는 이유만으로 전역 접근으로 판정하지 않는다. 버전 어댑터는 `semver`를 사용하며, YAML 변환 중 발생하는 알려진 별칭 입력 오류는 실패 진단으로 변환한다. 이 의존성들도 저장소 개발용이며 설치 스킬의 실행 의존성이 아니다.
