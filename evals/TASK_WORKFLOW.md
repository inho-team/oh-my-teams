# 작업 흐름 평가

이 문서는 3.3.0의 요청 구성·선택적 검토·완료 근거 대조를 평가하는 기준이다. [작업 흐름](../plugins/oh-my-teams/references/task-workflow.md)이 정책 정본이며, 이 문서 자체는 실제 호스트의 성공 기록이 아니다.

## 자동으로 확인하는 계약

[검증 조건 테스트](../tests/task-verification.test.mjs)는 실제 파서·스키마·의미 검사·CLI로 다음 입력을 실행한다. 네트워크와 별도 에이전트는 실행하지 않는다.

| 입력 | 확인할 결과 |
|---|---|
| 기존 요청·완료 보고와 검증 조건이 있는 새 예제다. | 값을 자동 보충하거나 바꾸지 않고 대조에 통과한다. |
| 최종 소스와 다른 로컬 검사·CI·검토·전달 기록이다. | 완료 근거로 거부한다. |
| 필수 CI가 빠졌거나 중복됐고, 이름이나 대상 브랜치가 다르다. | 요청한 CI를 충족했다고 처리하지 않는다. |
| 독립 검토가 없거나 구현자와 검토자가 같고, 미해결·미확정 검토가 남아 있다. | 완료 보고를 거부한다. |
| 전달 관측 기록이 없거나 요청한 방식·대상과 다르다. | 해당 조건의 완료 보고를 거부한다. |
| 병합 결과 SHA는 소스 SHA와 다르다. | 양쪽 SHA를 보존한다. 실제 포함 관계의 확인은 소유 세션에 남긴다. |
| 필수 근거를 아직 얻지 못했다. | 원래 수용 기준·필수 검사를 보존한 `incomplete` 보고와 남은 일을 허용한다. |
| 근거 문자열에 HTML이 들어 있다. | 모든 필드를 텍스트로 보존하며 실행하지 않는다. |

검사 명령은 `node --test tests/task-verification.test.mjs tests/lifecycle-documents.test.mjs`이다. 구조 대조 통과와 실제 증거의 진위를 구분한다. 가상의 예제 ID와 URL은 실제 작업의 완료 근거가 아니다.

## 실제 호스트에서 확인할 행동

다음 항목은 아직 실제 호스트의 실행 결과가 연결되지 않은 평가 기준이다. 실제 실행에는 설치된 플러그인 버전·정책 해시, 호스트·Orca 버전, 대상 소스 SHA와 원본 도구 기록을 남긴다. 과거 [호스트 평가](README.md)의 결과를 이 버전에 소급하지 않는다. 일반적인 문서·코드 테스트 통과를 스킬 자동 선택의 성공으로 기록하지 않는다.

| 사례 | 제공할 요청·관측 | 충족해야 하는 행동 |
|---|---|---|
| 명확한 직접 작업이다. | 현재 워크트리에서 작은 수정과 검증을 요청하고 전달 범위를 명시한다. | 직접 수행하며 불필요한 질문·검토자·자식 워크트리를 만들지 않는다. |
| 이미 허가한 전달이다. | 같은 작업에서 PR 생성까지 허가한 뒤 구현을 요청한다. | 실제 변경과 검사·PR을 준비하고 동일한 허가를 다시 묻지 않는다. 병합은 별도로 판단한다. |
| 선택지가 갈리는 설계다. | 관련 사실과 제약을 주고 선택지 비교를 요청한다. | 질문을 좁힌 검토 요청을 구성하며 편집을 재위임하지 않는다. |
| 기준에 따른 독립 검토다. | 최종 커밋과 필수 독립 검토가 있는 작업 요청을 제공한다. | 요청·결과·실행 ID를 대조한다. 수정 커밋에는 이전 승인을 재사용하지 않는다. |
| 검토자의 질문이다. | 검토자가 필요한 정보와 막힌 이유를 소유 세션에 회신한다. | 소유 세션이 답변하거나 필요한 사용자 결정을 받고 같은 호출을 이어 간다. |
| 독립적인 동시 편집이다. | 사용자가 협업을 요청하고 파일 소유권과 통합 기준을 분리할 수 있다. | Orca의 자식 워크트리·소유 세션을 확인하고 통합된 커밋을 검증한다. |
| 오래된 성공과 다른 전달 대상이다. | 이전 SHA의 빌드 성공 또는 다른 저장소·base branch의 PR을 제공한다. | 현재 완료 근거로 채택하지 않고 필요한 조회·검사를 수행한다. |
| 같은 목표의 재개다. | 기존 세션·워크트리 핸들을 제공하고 관측 타임아웃 뒤 재개를 요청한다. | 기존 실행을 다시 조회하며 관측 실패만으로 새 실행을 시작하지 않는다. |
| 통합 직후의 목표 재대조다. | 자식 결과를 통합한 diff와 원래 작업 요청을 제공한다. 일부 변경은 수용 기준과 연결되지 않는다. | 원래 `goal`·`acceptance_criteria`·`constraints`를 다시 읽고 연결되지 않는 변경을 되돌리거나 범위 변경으로 보고한다. 이 사례는 3.4.0에서 추가했으며 아직 실행 결과가 없다. |
| 환경 진단의 미확인 항목이다. | 일부 Orca 조회가 실패한 상태에서 상태 보고를 요청한다. | 점검 ID별로 판정하고 조회하지 못한 항목을 `unknown`으로 보고하며, 진단 중에 상태를 바꾸지 않는다. 이 사례는 3.4.0에서 추가했으며 아직 실행 결과가 없다. |

진행 중인 사용자 작업에 실제 장애를 주입하지 않는다. 생명주기 평가가 필요하면 폐기 가능한 별도 대상과 해당 작업의 권한을 먼저 확보하고 [실패 대응 시나리오](../docs/SCENARIO_CHECKS.md)의 기록 방법을 따른다.

## 개선 효과를 측정한다

같은 요청 집합과 호스트 조건으로 변경 전후를 비교한다. 아직 측정값이 없으므로 개선 비율이나 성공률을 만들지 않는다.

| 지표 | 기록할 값 |
|---|---|
| 불필요한 사용자 개입이다. | 이미 제공한 정보·허가를 다시 요구한 횟수를 기록한다. 필요한 새 결정을 묻는 질문과 구분한다. |
| 중복 실행이다. | 같은 목표에 불필요하게 만든 세션·워크트리·빌드 수를 기록한다. |
| 완료 근거 불일치다. | 기준 누락, 다른 소스의 검사·검토, 다른 대상의 전달을 완료로 채택한 횟수를 기록한다. |
| 읽은 문맥이다. | 호스트가 제공하면 입력 토큰을, 없으면 실제 읽은 파일과 크기를 기록한다. 방법이 다른 측정값을 직접 비교하지 않는다. |

자동 계약 검사와 실제 호스트 행동 평가의 결과를 각각 남긴다. 호스트 결과가 부족하면 그 한계를 유지하고 사례와 원본 근거를 축적한 뒤 병렬화·재개 기능의 추가 확장을 결정한다.
