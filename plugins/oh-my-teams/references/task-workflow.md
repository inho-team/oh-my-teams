# 작업 요청부터 검증한 전달까지

이 문서는 작업 범위를 구성하거나 검토를 요청하고 완료 근거를 대조할 때 읽는다. 일반 작업에 팀 세션이나 별도 상태 저장소를 추가하는 절차가 아니다. 작업 요청과 보고서는 판단 근거를 전달하며, 실행 상태는 Orca에서 확인한다.

## 요청을 구성한다

사용자의 요청, 같은 작업에서 이미 정한 결정과 저장소 지침을 먼저 읽는다. 목표는 사용자가 얻으려는 결과로, 수용 기준은 실제 파일·실행 결과로 확인할 수 있는 조건으로 적는다. 구현 방법을 사용자의 요구 사항으로 바꾸거나 이미 받은 허가를 다시 묻지 않는다. 목표, 외부 전달 대상이나 권한처럼 결과를 바꾸는 정보가 없을 때에만 소유 세션이 질문한다. 답변과 무관하게 진행할 수 있는 조사와 구현은 이어 간다.

| 확인한 정보 | 작업 요청에 기록할 위치 |
|---|---|
| 사용자가 얻으려는 결과와 현재 변경 범위다. | `goal`, `scope`에 기록한다. |
| 결과가 갖춰야 하는 동작과 보존할 계약이다. | 중복되지 않는 `acceptance_criteria`와 `constraints`에 기록한다. |
| 저장소 지침과 변경 범위에서 필요한 검사다. | `required_checks`에 이름과 실제 실행 명령을 기록한다. |
| 필수 CI의 이름과 검사 대상 브랜치다. | `verification.required_ci`에 기록한다. 미등록·조회 실패를 빈 목록으로 바꾸지 않는다. |
| 독립 검토가 필요한 이유와 허용된 검토 방식이다. | 필요할 때에만 `verification.independent_review`를 `true`로 기록한다. |
| 사용자가 허가한 전달 방식과 정확한 대상이다. | `delivery`에 기록한다. 전달이 있으면 `verification.delivery_receipt`를 `true`로 기록한다. |
| 사용자가 완료 조건으로 요구한 자식 워크트리 정리다. | `cleanup_required`에 기록한다. 현재 소유 워크트리 삭제를 완료 조건으로 만들지 않는다. |

새 작업 요청은 [검증 조건을 포함한 예제](documents/verified-task.example.yaml)를 바탕으로 구성한다. 필수 CI나 독립 검토가 없으면 각각 빈 배열과 `false`를 사용한다. 검증 조건이 없는 이전 요청도 읽을 수 있지만, 그 요청의 형식 검사 통과를 새 검증 조건의 충족으로 보고하지 않는다. 사용자가 범위를 변경하면 요청과 변경 근거를 함께 보존하며, 완료 보고를 통과시키려고 기준을 줄이지 않는다.

짧은 직접 작업에 YAML 문서를 매번 작성할 필요는 없다. 같은 목표·기준·검사·권한을 유지하면서 직접 처리한다. 세션 사이에 작업을 전달하거나 OMT 완료 문서로 대조할 때에는 `task_request`를 사용한다. 작업 중에는 변경 영향이 있는 코드·문서와 관련 검사만 읽고 실행하며, 종료할 때 저장소가 요구하는 전체 검사를 수행한다.

## 수행 방식을 선택한다

| 상황 | 소유 세션의 판단과 행동 |
|---|---|
| 목표와 구현 경로가 명확하고 현재 세션에서 순차적으로 처리할 수 있다. | 직접 구현하고 검증한다. 호출 횟수나 역할 수를 늘리지 않는다. |
| 설계 선택지가 갈리거나 독립적인 기준 대조가 필요하다. | 해당 질문과 자료만 좁혀 [consult](../skills/consult/SKILL.md)를 사용한다. advisor는 선택지를 비교하고 auditor는 고정된 결과를 대조한다. |
| 사용자가 협업을 요청했고 서로 의존하지 않는 편집을 동시에 진행할 수 있다. | [kickoff](../skills/kickoff/SKILL.md)에 따라 자식 워크트리에 범위·기준 커밋·통합 조건을 배정한다. 같은 파일의 동시 편집은 분리 근거가 아니다. |

검토가 유용하다는 이유만으로 병렬 편집을 시작하지 않는다. 자식 결과를 합친 뒤에는 통합된 최종 커밋에서 필요한 검사를 수행한다. 재개 시에는 기존 Orca 핸들과 Git 상태를 먼저 조회하고, 관측 실패로 새 실행을 만들지 않는다.

## 검토 요청을 구성한다

검토가 필요해지면 소유 세션이 현재 자료에서 요청을 구성한다. 사용자가 같은 배경을 다시 설명하게 하지 않는다. [검토 예제](documents/review-request.example.yaml)에 다음 정보를 넣는다.

- `question`에는 결정하거나 검증할 질문을 적는다. `facts`에는 변경 목적, 기준 커밋과 변경된 범위, 이미 확인한 결과를 적는다.
- `subject.commit`에는 검토할 전체 SHA를, `implementation_session_id`에는 실제 구현 실행 ID를 적는다. auditor는 이 커밋을 기준으로 읽는다.
- `acceptance_criteria`에는 이번 검토에 해당하는 원래 기준을 넣고, `constraints`에는 읽기 전용 범위와 특히 확인할 위험을 적는다.
- `evidence`에는 해당 diff, 파일, 검사 결과와 원래 작업 요청의 위치를 넣는다. 요청·회신 핸들과 원문 결과를 보존한다.

소유 세션이 요청과 결과의 ID·목적·커밋·구현 실행 ID를 대조한다. 지적은 실제 코드와 재현 근거로 판단하고, 수정하면 새 커밋을 다시 검토받는다. `changes_requested`와 `inconclusive`는 검토 통과가 아니다. 검토자가 질문하면 소유 세션이 답변하거나 필요한 사용자 결정을 받아 같은 호출로 전달한다. 독립 검토를 요구했지만 호스트에서 별도 실행을 제공하지 못하면 필수 남은 일로 보고한다.

## 완료 근거를 대조한다

[완료 예제](documents/verified-completion.example.yaml)의 다음 연결을 실제 관측에서 채운다. 보고서의 문자열이나 다른 세션의 성공 선언만 복사하지 않는다.

| 근거 | 소유 세션이 확인할 연결 |
|---|---|
| 최종 소스다. | `subject.commit`이 실제 최종 Git SHA와 같고, 검증할 변경이 미커밋 상태로 남아 있지 않은지 확인한다. |
| 로컬 검사다. | 통과한 `checks`의 `source_commit`이 최종 SHA와 같고, 이름·명령·로그가 원래 필수 검사와 대응하는지 확인한다. 검사 후 소스를 고쳤다면 영향을 받는 검사를 다시 수행한다. |
| CI다. | 요청한 CI 이름마다 실제 빌드 ID, 최종 소스 SHA, 대상 브랜치와 현재 성공 상태를 확인한다. 병합용 빌드는 원본 소스 SHA와 빌드 커밋의 연결도 확인한다. |
| 독립 검토다. | `reviews`에 최종 커밋의 요청·결과 ID, 구현·검토 실행 ID와 원문 위치를 기록한다. 원문이 해당 요청에 응답하고, 구현자와 검토자가 다르며, 미해결 지적이 없는지 확인한다. 이전 검토 원문은 보존하되 최신 승인으로 사용하지 않는다. |
| 전달이다. | `delivery.reference`의 실제 PR·커밋·산출물을 조회한 뒤 `receipt`에 방식·대상·소스 SHA·관측 시각·근거를 기록한다. `commit`과 `merge`에는 `delivered_commit`도 기록한다. 병합 결과 SHA는 소스 SHA와 다를 수 있으므로 양쪽의 연결을 확인한다. |

전달 대상 표기는 작업 시작부터 종료까지 동일하게 사용한다. 예를 들어 `owner/repository/main`이라는 PR 대상을 요청했으면 실제 PR의 저장소와 base branch를 조회해 그 표기로 기록한다. 임의 URL을 적고 대상을 확인했다고 주장하지 않는다. 산출물은 요청한 위치와 실제 파일을 확인한다. 전달 관측 기록은 네트워크 조회를 대신하는 인증서가 아니다.

저장소 개발용 변환기가 있는 환경에서는 완료 보고에 `--task`, 검토 결과에 `--request`를 연결해 대조한다. 명령은 설치 플러그인의 필수 의존성이 아니며, 없는 호스트에서는 같은 규칙을 직접 대조한다. 구조 검사는 문자열로 기록한 근거의 존재·진위, 실제 사용자 허가와 실행 ID의 독립성을 인증하지 않는다. 소유 세션이 Orca·Git·CI와 원문을 확인한다.

필수 근거가 없으면 `incomplete`와 정확한 남은 일을 기록한다. 결과 전달과 정리는 별도로 판단하며 [close](../skills/close/SKILL.md)의 회수 조건을 따른다. 완료 판단을 통과시키기 위해 필수 CI·검토·전달 조건을 해제하지 않는다.
