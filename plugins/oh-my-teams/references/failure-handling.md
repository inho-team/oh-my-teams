# 실패 상황의 판단 기준

소유 세션은 오류 메시지와 함께 Git HEAD, Orca의 전체 ID·인스턴스 식별자, CI 빌드 ID처럼 이미 확인한 대상을 보존한다. 관측 실패와 실제 실행 실패를 구분하며, 확인되지 않은 상태를 정상·종료·성공으로 바꾸지 않는다. 상태와 실행의 정본은 해당 호스트와 Orca이며 별도 실행 등록부를 만들지 않는다.

## CI 결과를 확인할 때

| 확인한 사실 | 다음 행동 |
|---|---|
| 필수 검사의 상태 목록이 비어 있고 빌드 ID도 없다. | 검사 미등록으로 보고한다. 실행 경로와 등록 조건을 확인하고, 등록이나 인증에 필요한 정보가 없으면 소유 세션이 사용자에게 요청한다. 실행 중이라고 추정하거나 같은 빈 조회를 진전으로 반복 보고하지 않는다. |
| 빌드 ID가 있고, 해당 빌드의 현재 상태가 대기 중이거나 실행 중이다. | 같은 빌드를 조회한다. 관측 타임아웃이나 출력 단절만으로 빌드를 새로 시작하지 않는다. 확인한 ID, 상태와 관측 시각을 보고한다. |
| 빌드가 실패했다. | 실패한 단계와 로그를 확인한다. 코드 결함과 CI 환경·인증 문제를 구분하고 원인에 맞춰 처리한다. 코드가 바뀌면 새 커밋의 검사가 필요하다. |
| 빌드가 성공했다. | 검사 결과가 현재 PR의 소스 HEAD와 대상 브랜치에 대응하는지 확인한다. PR 병합 결과를 검사하는 CI에서는 소스 HEAD와 생성된 병합 커밋을 구분해 연결한다. 이전 커밋의 성공을 새 결과의 승인으로 쓰지 않는다. |
| 검사가 취소되거나 건너뛰어졌다. | 필수 검사 통과로 취급하지 않는다. 요구된 검사가 실제로 수행됐는지 확인한다. |
| 조회가 인증 오류나 네트워크 오류로 실패했다. | 결과를 확인할 수 없다고 보고한다. 상태 목록이 비어 있다는 뜻으로 바꾸지 않으며, 이미 아는 빌드 ID를 보존한다. |

검사를 기다린다는 보고에는 현재 확인한 빌드나 작업의 식별자가 있어야 한다. 식별자나 현재 실행 근거가 없다면 검사 시작을 확인하지 못한 것으로 보고한다. 사용자가 성공했다고 전달한 경우에도 가능한 공식 결과에서 검사 대상과 성공 여부를 대조한다.

## 중단 후 재개할 때

현재 워크트리의 경로, 전체 ID, 인스턴스와 소유 세션을 Orca에서 다시 확인한다. Git HEAD, 미커밋 변경과 이미 전달한 결과를 대조하고, 같은 목표를 수행 중인 세션이 있으면 그 실행을 중복 생성하거나 배정하지 않는다. 터미널 연결이나 화면 출력만으로 실제 진전이나 작업 완료를 판단하지 않는다.

목록에 세션이 없거나 조회가 불완전해도 종료됐다고 추정하지 않는다. 기존 핸들을 다시 조회하거나 해당 호스트에서 확인한다. 실제 종료나 핸들 소멸이 확인된 뒤에만 재시작 여부를 판단한다. 여전히 확인할 수 없다면 기존 작업을 보존하고 소유권과 재개에 필요한 정보를 요청한다.

## 삭제 결과가 불명확할 때

삭제 요청이 타임아웃됐거나 응답이 끊겼다면 추가 삭제를 보내기 전에 같은 호스트의 Orca 목록과 정확한 인스턴스를 조회한다. 완전한 목록에서 해당 인스턴스의 제거가 확인되면 제거 결과를 보고한다. 목록이 불완전하거나 같은 인스턴스인지 확인되지 않으면 보존 상태와 남은 확인 사항을 보고한다. 이름이나 경로가 같아도 인스턴스가 바뀌었으면 이전 요청의 대상과 다르다.

삭제를 반복해서 성공 여부를 확인하지 않는다. 추적되지 않거나 무시된 파일, 미전달 커밋과 종료가 확인되지 않은 세션이 있으면 회수하지 않는다. 결과 전달과 정리 상태는 각각 보고하고, 현재 소유 세션이 서 있는 워크트리는 제거하지 않는다. Goal 상태는 호스트 규칙을 따르며, 확인할 수 없는 필수 검사를 완료로 바꾸거나 사용자의 요청 없이 일시중지하지 않는다.
