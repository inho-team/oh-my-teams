# 한국어 최종 결과 작성

PM이 한국어 사용자에게 개발 작업 결과를 전달할 때 읽는다. 이 문서는 실행 계약이나 증거 기준을 바꾸지 않고, 이미 확인한 결과를 읽기 좋은 한국어로 옮기는 방법만 정한다.

## 결과의 흐름

첫 문단에서 무엇이 끝났고 사용자에게 어떤 효과가 생겼는지 말한다. 그다음 필요한 만큼만 아래 흐름을 사용한다.

1. **요약**: 바뀐 동작과 현재 상태를 두세 문장으로 설명한다.
2. **왜 바꿨는지**: 관측된 문제와 원인을 연결한다. 단순히 파일이나 커밋 목록을 반복하지 않는다.
3. **바꾼 것과 남긴 것**: 새 책임과 기존 책임, 적용 범위와 비범위를 구분한다. 사용자가 특별히 보존하라고 한 동작은 별도로 밝혀 준다.
4. **검증 결과**: 원래 요청의 수용 조건 순서대로 입력 또는 시나리오, 기대 동작, 실제 결과를 한 묶음으로 쓴다.
5. **남은 사항**: 실제로 남은 배포, 외부 확인, 미해결 위험만 적는다. 없으면 이 절은 생략한다.

위 제목을 매번 모두 쓰거나 같은 표현으로 고정하지 않는다. 작은 변경은 짧은 문단과 검증 한 줄이면 충분하다. 여러 정책이나 책임 경계가 얽힌 작업은 `바꾼 것`과 `그대로 둔 것`을 나누면 읽기 쉽다.

## 문장 원칙

- 작업 과정보다 결과를 먼저 쓴다. `조사했습니다`, `에이전트를 실행했습니다`로 시작하지 않는다.
- 기술 용어는 동작을 정확히 설명할 때만 남긴다. `accepted settlement`, `gate`, `workflow revision` 같은 내부 상태는 사용자에게 필요한 뜻으로 풀어 쓴다.
- 원인, 변경, 효과를 이어 쓴다. 예: `중복 필터가 정상 결과를 잘라 내고 있어 제거했고, 이제 엔진 결과가 그대로 전달됩니다.`
- 확인한 사실과 추정을 섞지 않는다. 실행한 검사는 `통과`, 실행하지 못한 외부 검증은 `배포 뒤 확인 필요`처럼 구분한다.
- 검증은 `테스트 통과`로 뭉개지 않는다. 중요한 시나리오마다 무엇을 넣었고 무엇이 남거나 사라졌는지 결과를 적는다.
- 파일명, 커밋, 검사 명령, 모델 사용량은 근거로 유용할 때만 짧게 덧붙인다. 본문의 주인공으로 만들지 않는다.
- 사용자가 이슈 본문이나 댓글에 붙일 글을 원하면 그대로 복사할 수 있게 쓴다. 실제로 외부 이슈에 게시하지 않았다면 게시했다고 표현하지 않는다.
- 실패나 부분 완료도 같은 흐름으로 쓴다. 끝난 범위, 막힌 원인, 확인된 영향, 다음에 필요한 한 가지 결정을 분명히 한다.
- 진행 상태는 보고 직전에 확인한 Goal과 worker 관측값으로만 표현한다. 계획이나 다음 단계가 있어도 `live` worker가 0명이면 “진행 중”이라고 쓰지 않는다. Goal이 `blocked`이면 그대로 밝히고, 계획·완료된 변경·현재 실행을 별개의 사실로 서술한다.

## 예시 뼈대

```text
요약
중복으로 적용되던 후처리를 제거했습니다. 이제 생성 단계가 정한 결과가 중간에서 다시 잘리지 않습니다.

왜 바꿨는지
예전 후처리는 현재의 역할 구분이 생기기 전에 만들어져, 정상 후보까지 제외하고 있었습니다.

바꾼 것
- 중복 상한과 사후 제거를 없앴습니다.
- 결과 역할은 생성 단계가 정한 값을 그대로 사용합니다.

그대로 둔 것
- 데이터 출처 확인과 저장 계약 상한은 계속 적용됩니다.

검증 결과
- 조건 A: 기대한 후보가 끝까지 남았습니다.
- 조건 B: 제외 사유에 이전 상한 코드가 더 이상 나타나지 않았습니다.

남은 사항
운영 배포 뒤 실제 응답 한 건을 재측정해야 합니다.
```

이 뼈대는 문체와 정보 순서의 예시다. 실제 보고에서는 사용자의 용어와 원래 수용 조건을 사용하고, 확인하지 않은 수치나 결과를 채워 넣지 않는다.
