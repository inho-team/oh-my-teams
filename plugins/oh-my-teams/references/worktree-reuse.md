# 워크트리 자동 재사용과 회수

PM은 등록된 PM 체크아웃에서 `role-worktree-create`에 새 작업의 workflow와 task를 지정합니다. 런타임은 같은 킥오프에서 수용된 작업과 완료되어 보관된 다른 킥오프를 먼저 조사합니다. 같은 킥오프에서는 이전 workflow의 최종 수용을 기다리지 않고 수용된 작업의 워크트리를 후보에 포함합니다. 다만 현재 Git 기준 커밋에 그 워크트리의 HEAD가 포함되어 있고 Orca의 실행·터미널 목록과 종료 증명이 안전해야 실제로 재사용합니다. 적격 후보를 찾으면 기존 워크트리를 사용합니다. 후보의 현재 목록을 증명하지 못하면 새 워크트리를 만들지 않고 조정을 요구합니다. 다른 후보가 없으면 거부 사유를 기록한 뒤 새 워크트리를 만듭니다. `--fresh-reason`은 이 조사를 건너뛰는 옵션이 아닙니다. `--worktree`로 특정 후보를 지정해도 같은 증명을 적용하며, 지정한 후보가 거부되면 다른 워크트리를 조용히 생성하지 않습니다.

같은 작업을 반려한 뒤 역할을 상향할 때에는 검토가 끝난 기존 워크트리를 사용합니다. 이전 역할의 종료, 현재 워크트리 신원과 소유권, 깨끗한 Git 상태 및 기준 커밋을 증명한 뒤 다음 역할의 세션을 엽니다. 같은 역할의 수정과 재시도는 기존 작업에 연결된 워크트리를 유지합니다.

## 참여 조건과 증명

자동 재사용의 원천은 이 프로토콜로 등록된 킥오프여야 합니다. 등록 당시의 조직 파일 정본과 프로토콜 표식, 해당 워크트리의 실행 기록을 확인합니다. 완료 시점에는 실제 workflow의 작업별 수용 결정과 통합 결정 및 구성 작업의 revision·attempt·acceptedResult를 대조하여 보관 증명을 고정합니다. 이전 버전으로 등록된 킥오프를 새 버전에서 해제하는 것만으로는 참여 기록이 생기지 않습니다. 과거 기록을 직접 수정하여 소급 등록하지 않습니다.

다른 활성 킥오프의 워크트리는 후보가 아닙니다. 보관된 원천도 실제 Orca와 Git을 다시 조사합니다. 정확한 instance와 execution host, 현재 부모, lineage, 자식 워크트리 부재, 모든 Run과 Dispatch 및 연결 터미널의 종료, 깨끗한 작업 디렉터리와 통합 HEAD의 포함 관계를 증명해야 합니다. 현재 터미널 목록이 비었다는 사실만으로 과거 실행의 종료를 추정하지 않습니다. 외부 터미널의 완료된 Dispatch가 `missing_status`로 남아 있으면 현재의 완전한 빈 목록에 더해 정확한 instance·host, PTY incarnation, runtime·tab, Dispatch release와 `ptyKilled: true` 영수증을 모두 대조합니다. 현재 worktree 조회와 전역 terminal 조회 및 각 후보의 `terminal list --worktree id:...` 영수증을 따로 보존합니다. 전역 조회에 대상 host가 빠져도 과거 snapshot으로 보강하지 않고 현재 후보별 조회의 hostScope·runtime·완전성과 모든 행의 worktree·host를 검증합니다. 현재 worktree 조회와 후보별 terminal 조회의 hostScope를 따로 보존하고 대상 host가 양쪽 hostIds에 포함되며 omittedHostIds에 없음을 확인합니다. 두 조회는 완전하고 같은 runtime에서 와야 하며 외부 종료 증명은 그 runtime에도 일치해야 합니다. 대상 외 원격 host가 빠진 것만으로 검증된 local 후보를 거부하지 않습니다. 이 결속이 없거나 살아 있는 터미널·다른 Dispatch가 있으면 거부합니다. 정확한 instance에 대응하는 종료 영수증이 있어야 합니다. 누락되거나 읽을 수 없는 증명은 후보의 거부 사유로 남습니다.

조직 디렉터리의 `worktree-reuse-decisions.json`에는 선택 결과와 후보별 거부 사유가 기록됩니다. 보관 증명은 수용 이력을 고정하며, 현재 프로세스나 Git 상태를 대신 증명하지 않습니다.

## 경합과 중단

이전, 킥오프 해제, 킥오프 회수, 역할 회수, 생성 실패 회수와 브랜치 정리는 조직 파일의 realpath에 대응하는 공통 잠금을 사용합니다. 잠금과 저널은 조직 파일이 있는 디렉터리에 저장됩니다. 따라서 조직 파일의 경로 별칭으로 호출해도 같은 잠금을 사용합니다. 조직 파일이 없는 기존 저장소의 브랜치 정리는 로컬 어댑터가 주 Git 체크아웃임을 증명한 뒤 같은 `.omt` 디렉터리를 사용합니다. 조직 설정 파일을 새로 만들지 않으며, 나중에 조직이 등록되어도 잠금 위치는 같습니다. 명시한 조직 파일을 읽을 수 없거나 주 저장소의 앵커를 증명하지 못하면 브랜치를 보존합니다.

외부 변경 전에 전환 저널의 준비 기록을 파일과 디렉터리에 동기화합니다. Orca의 identity 선택자로 변경한 뒤 독립 조회로 결과를 확인해야 완료 기록을 남깁니다. 이전 완료 기록은 원천 킥오프의 이후 회수와 브랜치 정리에서 해당 자원을 계속 제외하는 근거입니다. 변경 응답이 사라지거나 사후 조회가 일치하지 않으면 준비 기록을 남겨 후속 변경을 차단합니다.

미완료 전환이 있으면 자동 재시도나 새 워크트리 생성으로 우회하지 않습니다. PM은 저널, 현재 Orca 신원과 부모, 세션·Dispatch, Git 상태를 이사에게 보고하고 대조해야 합니다. 이 버전에는 불명확한 전환을 자동으로 완료 처리하는 복구 명령이 없습니다. 실제 상태 확인 없이 잠금이나 준비 기록을 삭제하지 않습니다.

이 보장은 같은 프로토콜에 참여하는 호출 사이에 적용됩니다. Orca의 `worktree set`과 제거 명령에는 기대 부모를 원자적으로 비교하는 조건이 없으므로, 이미 실행 중인 구버전이나 수동 Orca 변경까지 공통 잠금으로 막을 수 없습니다. 출처를 증명하지 못하는 `manual` lineage를 포괄적으로 신뢰하지 않으며, 정확한 신원과 변경 후 lineage가 완료 저널과 일치하는 경우에만 이전 증명으로 사용합니다.

## 운영체제와 내구성

파일시스템의 디렉터리 동기화를 실제로 시도하여 지원 여부를 확인합니다. 지원하지 않으면 내구성이 필요한 이전과 회수는 외부 변경 전에 `worktree-durability-unavailable`로 거부합니다. 파일 동기화만 수행한 뒤 지원한다고 표시하거나 새 워크트리로 조용히 우회하지 않습니다. 일반 킥오프 보관은 계속할 수 있지만 해당 보관본은 재사용할 수 없다고 표시합니다. 운영체제 이름만으로 지원 여부를 단정하지 않습니다. 조직 파일이 없는 기존 저장소의 브랜치 정리는 주 Git 디렉터리의 실제 파일 신원과 동일한 미래 조직 잠금 아래에서만 별도로 처리합니다. fsync 미지원 호환 경로는 조직 파일·등록부·보관 이력·전환 저널 자원이 모두 없는 경우에 한정하며, 기존 Git 통합·안전 삭제 및 사후 확인을 유지합니다. 새 프로토콜 표식이나 자원이 있으면 이 경로를 사용할 수 없습니다.

등록 당시 `reuseProtocol`이 없던 legacy 킥오프의 **같은 작업** 상향·역할 회수에는 제한된 호환 경로가 있습니다. 디렉터리 동기화 능력 검사 자체가 미지원으로 끝난 경우에만 검토하며, 준비 기록을 쓰다가 실패한 경우에는 이 경로로 넘어가지 않습니다. 현재 instance와 부모 instance, CLI explicit lineage, 서버의 생성 시각 이후에 기록된 실제 legacy Dispatch, 같은 PM·workflow·task의 전체 실행 이력을 결속해야 합니다. `role-terminal` 기록에 task ID가 없으면 동일한 터미널의 후속 `worker-start`가 같은 task·workflow·PM 소유자에 속하는지와 시각 순서를 함께 확인합니다. worker의 task ID가 없거나 다른 task의 기록이 섞이면 허용하지 않습니다. 같은 경로를 나중에 재생성했거나 과거 소유 이력이 모호하면 거부합니다. 어떤 전환 저널이라도 해당 자원을 소유하거나 다른 작업·킥오프의 이력이 있으면 사용할 수 없습니다. protocol 표식이 없는 것만으로는 허가하지 않습니다.

이 호환 경로도 공통 잠금과 기존 수용·검토·Git·전체 Dispatch·정확한 터미널 종료 검사를 유지하고, 외부 변경 직전 현재 신원과 부모를 다시 조회합니다. 결과의 `legacyLifecycle`은 `mode: legacy-same-task`, `durable: false`와 실제 미지원 이유를 명시합니다. 새 프로토콜의 내구성을 지원한다고 표시하지 않으며 새 프로토콜의 완료 저널도 만들지 않습니다. 신규 자원 생성이나 교차 킥오프 이전에는 적용하지 않습니다. 오래된 기록이 이 증명을 제공하지 못하면 자원을 보존하고 PM에게 누락된 근거를 보고합니다.

## Agy의 폴더 신뢰

신뢰 기록의 정확한 경로가 확인된 경우에만 사전 예측에서 신뢰한 폴더로 취급합니다. 알 수 없는 값은 참이 아니며, 조상 경로가 신뢰되었다는 사실만으로 자식 워크트리를 신뢰한다고 판단하지 않습니다. 실제 화면에서 질문이 나오면 기존 감독자의 `prompt-answer` 절차를 따릅니다. 인식되지 않은 화면이나 증명되지 않은 감독 관계에서는 키를 보내지 않고 차단 이유와 다음 행동을 보고합니다. 플러그인은 사용자의 설정 파일에 신뢰 항목을 직접 쓰지 않습니다.

현재 회귀 검사는 실제 Git 저장소와 런타임이 생성한 보관 기록을 사용하고 Orca 전송 계층은 대체합니다. 실제 두 킥오프 사이의 Orca 이전, Agy의 조상 경로 신뢰 범위와 화면, Linux·macOS·Windows CI 결과는 별도의 감독 검증 근거가 필요합니다. 이 문서의 프로토콜 설명을 그 실측의 통과 증거로 사용하지 않습니다.

## 같은 PM을 다시 등록한 경우의 소유권

같은 PM ID와 instance를 다시 사용해도 등록 회차는 별개입니다. 후보마다 registrationSeq·createdAt·kickoffHash와 실제 launch 시각을 대조하고, 수용된 workflow·task·attempt·revision·acceptedResult 및 실행 ID를 결속합니다. 첫 등록에서 전달하지 않은 child는 다음 등록의 전달 커밋에 포함되더라도 회수할 수 없습니다. 첫 보관본에서는 `head-not-delivered`를 유지하고, 다음 보관본에서는 원천 등록 귀속을 증명하지 못했다는 이유로 보존합니다. 보관 증명에 없는 자식이나 출처가 모호한 과거 실행도 보존합니다.

보관 디렉터리의 인도 요약 문서처럼 PM 등록 신원이 없는 기록은 소유 증명에서 제외하고 구체적인 사유를 남깁니다. 다른 기록의 형식 오류만으로 검증된 후보를 일괄 차단하지 않지만, 대상 PM의 등록 이력이 손상되어 회차 경계를 알 수 없으면 해당 후보를 보존합니다. 이미 이전된 자원은 완료 저널의 원천·목표 등록과 현재 신원·부모를 따로 대조합니다. task가 없는 자원은 해당 등록 구간의 독점적인 역할 터미널 실행 이력이 있어야 하며, PM 자체에도 더 나중의 재등록이 없어야 합니다.

조직에 등록된 자원의 브랜치 정리는 전달 문서와 Git 포함 관계에 더해 완료된 회수 저널의 정확한 branch·HEAD·등록 소유 증명을 요구합니다. 체크아웃이 남아 있거나 원격 tip이 증명된 로컬 tip과 다르면 로컬·원격 브랜치를 모두 보존합니다. `force`는 문서 확인을 우회할 수 있어도 자원의 출처를 대신 증명하지 않습니다. 조직과 프로토콜 자원이 없는 저장소의 기존 Git 기반 호환 경로는 별도로 유지합니다.
