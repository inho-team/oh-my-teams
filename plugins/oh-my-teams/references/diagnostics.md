# 환경 진단

이 문서는 팀 작업을 시작하거나 재개하기 전, 또는 상태 조회 결과가 예상과 다를 때 실행 환경을 점검하는 절차다. 진단은 현재 상태를 관측해 보고하는 일이며 상태를 바꾸는 수리가 아니다. 실제 실행 상태는 Orca에, 소스와 전달 결과는 Git·PR·CI에 있다.

## 점검 항목

각 항목은 고정된 ID로 보고한다. ID는 기록과 비교에 사용하므로 바꾸지 않고, 설명과 세부 관측 문구는 상황에 맞게 작성한다.

| ID | 확인할 내용 | 판정 기준 |
|---|---|---|
| `orca-cli-guide` | 사용 중인 Orca CLI 버전에 맞는 `orca-cli` 가이드를 읽었는지 확인한다. | 가이드를 읽지 못했으면 이후 Orca 명령을 추측으로 실행하지 않는다. |
| `orca-runtime-match` | CLI가 현재 앱과 같은 Orca 런타임과 실행 호스트를 가리키는지 확인한다. | 연결 대상이 다르거나 확인할 수 없으면 자식 세션 배정을 완료로 보고하지 않는다. |
| `worktree-managed` | 현재 워크트리의 경로와 전체 ID가 그 앱의 관리 대상으로 조회되는지 확인한다. | 조회되지 않는 워크트리를 소유한다고 보고하지 않는다. |
| `session-handles` | 기존 세션·터미널 핸들이 Orca 목록에서 대조되고 `orphaned` 상태가 아닌지 확인한다. | 핸들이 보이지 않는다는 이유만으로 종료됐다고 판단하지 않는다. |
| `git-state` | 브랜치, HEAD, 수정된 파일과 추적되지 않는 중요한 파일을 확인한다. | 미전달 변경이 있으면 보존 대상으로 표시한다. |
| `host-plugin` | 현재 호스트에서 설치된 OMT 스킬과 참조 문서를 읽을 수 있는지 확인한다. | 읽지 못한 문서의 규칙을 적용했다고 보고하지 않는다. |
| `ci-visibility` | 필수 CI의 빌드 목록과 상태를 조회할 수 있는지 확인한다. | 조회 실패, 미등록과 빌드 실패를 [실패 상황의 판단 기준](failure-handling.md)에 따라 구분한다. |

작업에 필요한 항목만 점검한다. 예를 들어 자식 워크트리를 만들지 않는 상태 조회에서는 `session-handles`의 자식 대조를 생략할 수 있으며, 생략한 항목은 생략했다고 보고한다.

## 판정

각 항목은 `pass`, `warn`, `fail`, `unknown` 중 하나로 판정한다.

- `pass`는 실제 관측으로 조건을 확인했다는 뜻이다.
- `warn`은 작업을 진행할 수 있지만 사용자나 소유 세션이 알아야 하는 차이가 있다는 뜻이다.
- `fail`은 조건이 충족되지 않았음을 관측했다는 뜻이다.
- `unknown`은 조회가 실패했거나 불완전해서 판단할 수 없다는 뜻이다. 조회하지 못한 항목을 `pass`나 `fail`로 채우지 않는다.

`fail`이나 `unknown`이 있으면 해당 항목에 의존하는 작업을 시작하지 않는다. 관측 실패만으로 같은 세션이나 워크트리를 새로 만들지 않는다.

## 진단과 수리를 분리한다

진단하는 동안에는 세션 종료, 워크트리 삭제, 설정 변경처럼 상태를 바꾸는 조치를 실행하지 않는다. 각 `warn`·`fail` 항목에는 확인한 사실과 가능한 수리 방법을 제안으로 기록한다. 수리 방법 중 사용자가 직접 실행해야 하는 조치와 소유 세션이 허가 범위 안에서 실행할 수 있는 조치를 구분한다.

플러그인은 사용자 설정 파일을 직접 쓰지 않으므로, 설정 변경이 필요한 수리는 사용자에게 필요한 변경만 안내한다. 수리를 실행한 뒤에는 같은 ID로 다시 진단하고, 수리 전후의 판정을 함께 보고한다. 수리를 실행했다는 사실만으로 조건이 충족됐다고 보고하지 않는다.
