# 자문 호출 계약

역할이 조직에서 가장 비싼 모델에게 결정 관문에서만 자문을 구하는 규칙이다. 이 문서가 정본이며 역할 스킬은 여기를 참조한다.

## 왜 따로 두는가

주도 역할(PM)은 kickoff가 끝날 때까지 이어지는 긴 세션이다. worker를 기다리며 감독할 때마다 누적된 컨텍스트 전체가 다시 입력되므로, 이 세션에 가장 비싼 모델을 두면 판단이 필요 없는 감독 턴까지 그 모델의 요금으로 처리된다. 자문 호출은 이 구조를 뒤집는다. 긴 세션은 주도 모델(예: Sol, Opus)이 맡고, 프론티어 모델(예: Astra, Fable)은 짧은 브리프 하나만 받아 한 번 답하고 끝난다.

`assist`와는 방향이 반대다. `assist`는 역할이 더 싼 GPT-OSS에게 조사와 초안을 맡기는 호출이고, `advise`는 역할이 더 비싼 모델에게 판단을 묻는 호출이다.

## 런타임이 강제하는 것

`scripts/worker.mjs`의 `advise`는 다음을 순서대로 검사하고, 하나라도 어긋나면 모델을 호출하지 않고 실패한다.

1. 브리프가 `schemaVersion: 1`, 소문자·숫자·하이픈으로 된 `id`, 2000자 이하의 `question`, 12000바이트 이하의 `summary`를 갖추어야 한다. `files`는 상대 경로 최대 8개, `options`는 문자열 목록이며 둘 다 생략할 수 있다.
2. 조직의 `advisors.<role>` 허용 목록에 프로필이 있어야 한다. **목록이 비어 있거나 역할이 빠져 있으면 그 역할의 호출은 전부 거부된다.**
3. `kind`가 `plan`, `design`, `review`, `unblock` 중 하나여야 한다.
4. 공유 조정자 상태 디렉터리가 있어야 하고, 그 안의 자문 예산(`policy.adviceBudget`, 생략하면 6)에 남은 칸이 있어야 한다.

```text
node <runtime> advise --org <organization.json> --brief <brief.json> --repo <worktree> --state <pm-state> --role <role> --kind <kind> [--profile <profile>]
```

여섯 인수가 모두 필수이고 `--profile`만 선택이다. `--profile`을 생략하면 허용 목록의 첫 항목을 쓴다.

요약이 12000바이트를 넘으면 잘라서 보내지 않고 거부한다. 대화 전문을 붙여 넣으면 싼 모델이 들고 있어야 할 컨텍스트를 비싼 모델에게 다시 보내게 되어, 이 계약을 둔 이유가 사라지기 때문이다.

예산 칸은 호출 전에 차지하며, 호출이 실패해도 돌려받지 않는다. 실패한 호출도 할당량을 이미 썼기 때문이다. 예산이 바닥나면 가진 근거로 결정하거나 상위(PM은 사용자)에게 보고한다.

## 브리프 작성

```json
{
  "schemaVersion": 1,
  "id": "wave-split",
  "question": "마이그레이션을 한 파동으로 보낼지 두 파동으로 나눌지 결정해야 한다.",
  "summary": "두 task가 같은 스키마 파일을 고친다. 전체 검사는 9분 걸린다. PL은 두 파동을 제안했다.",
  "files": ["docs/plan/migration.md"],
  "options": ["한 파동", "두 파동"]
}
```

- `question`에는 결정할 내용 하나만 쓴다.
- `summary`에는 결정에 필요한 사실, 이미 시도한 것과 제약만 쓴다.
- `files`에는 자문자가 직접 읽어야 하는 파일만 고른다. 파일을 넘기면 답변에 실제 줄을 인용해야 하고, 인용이 없거나 대조에 실패하면 결과가 저장되지 않는다.

## 호출하는 시점

자문은 되돌리기 비싼 결정 앞에서만 호출한다.

| `kind` | 호출하는 시점 |
|---|---|
| `plan` | PM이 목표를 task로 나눈 계획을 확정하기 전, PL이 파동과 의존성을 확정하기 전 |
| `design` | Senior가 인터페이스나 변경 순서를 정할 때 대안이 둘 이상 남은 경우 |
| `review` | 병합이나 최종 수용 직전에 검토 판정이 갈리거나 위험이 큰 경우 |
| `unblock` | 같은 실패가 반복되어 접근 방법을 바꿔야 하는 경우 |

진행 상황 확인, 보고 취합, 검사 실행처럼 판단이 필요 없는 일에는 호출하지 않는다.

## 결과를 다루는 방법

결과는 `decision`(`proceed`·`revise`·`stop`·`escalate`), `recommendation`, `rationale`, `risks`, `citations`로 구성되며 공유 상태의 `advice` 아래에 기록된다. **자문은 승인이 아니다.** 호출한 역할이 결과를 검증하고 결정을 책임지며, 수용 관문(`gate-check`, `accept`)은 자문 기록을 승인 근거로 읽지 않는다. 자문을 따르지 않기로 했다면 그 이유를 보고에 남긴다.

`usage-report`는 자문 기록의 사용량을 호출한 역할의 사용량으로 함께 집계한다.

## 조직에 설정하기

`advisor-codex`와 `advisor-claude` 프리셋이 역할별 모델과 자문 허용 목록을 함께 정한다. 설정 방법은 [adjust](../skills/adjust/SKILL.md)의 「역할과 프리셋」을 따른다. 허용 목록을 직접 고칠 때에는 `advisors`에 역할별 프로필 ID 목록을 적는다. `assistants`와 달리 모델 제한은 없다.
