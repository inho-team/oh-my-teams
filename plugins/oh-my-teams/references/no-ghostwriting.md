# 지시문에 구현을 대신 쓰지 않는 규율

출처: [pumasi](https://github.com/fivetaku/pumasi), MIT 라이선스.
pumasi의 "복붙형 instruction 금지" 규칙과 합리화 차단표를 oh my teams의 역할 구조에 맞게 한국어로 옮겼다.
합리화 차단표 형식은 pumasi가 obra/superpowers에서 가져온 것이다.

## 핵심 규칙

배정하는 역할은 **무엇을 만들지와 무엇으로 확인할지**를 쓰고, **어떻게 구현할지는 받는 역할에게 맡긴다.**
지시문, task의 `instruction`, 설계 결과, 검토 finding에 완성된 구현을 넣어 받는 역할을 옮겨 적는 도구로 만들지 않는다.

이 규율이 필요한 이유는 두 가지다.

- **비용:** 배정하는 역할은 대개 더 비싼 모델이다. 구현을 지시문에 대신 쓰면 비싼 모델이 구현 토큰을 이미 쓴 것이고, 받는 역할의 실행은 비용만 더한다.
- **검토 독립성:** 런타임은 구현 실행과 검토 실행의 ID가 같으면 검토를 거부한다. 그러나 PM·PL·Senior가 지시문에 쓴 코드를 Junior가 옮기면, 실제 작성자가 그 결과를 검토하거나 수용하게 되므로 이 검사를 형식만 남기고 우회한다.

## 지시문에 넣어도 되는 것

- 목표, 수용 기준, 비목표, 제약과 검사 명령
- 공개 인터페이스: 함수·클래스 시그니처, 타입·스키마 선언, 파일 경로와 export 이름
- 반드시 써야 하는 라이브러리와 그 import 한 줄, 쓰면 안 되는 대안
- 기존 코드의 위치(경로와 줄, `contextRefs`)와 재사용해야 할 helper 이름
- 실패를 재현하는 입력, 기대 출력, 실패한 검사의 로그 꼬리

## 지시문에 넣지 않는 것

- 함수·메서드의 본문, 완성된 파일, 적용하기만 하면 되는 diff나 patch
- 렌더링 마크업, 스타일 구현, 비즈니스 로직 구현
- "아래 코드를 그대로 작성한다" 같은 전사 지시
- 규칙을 지키는 척하며 주석, 예시, 의사코드에 사실상 완성된 구현을 숨기는 것. 문구가 아니라 의도를 기준으로 판정한다.

## 합리화 차단표

지시문을 쓰다가 아래 생각이 들면 멈추고, 인터페이스와 수용 기준만 남긴다.

| 떠오르는 생각 | 실제로 일어나는 일 | 대신 할 일 |
|---|---|---|
| "내가 짜는 게 더 빠르다" | 비싼 모델이 구현 비용을 이미 냈고, 받는 역할은 옮겨 적기만 한다. | 하위 역할이 없는 실행이면 깊이 규칙대로 직접 하고, 있으면 배정한다. |
| "본문 한 줄뿐이니 써 주자" | 한 줄이 함수가 되고 함수가 파일이 된다. | 시그니처와 기대 동작에서 멈춘다. |
| "설명보다 코드가 명확하다" | 복잡한 로직일수록 받는 역할이 이해하고 구현해야 검토가 의미를 가진다. | 입력·출력·경계 조건을 수용 기준으로 풀어 쓴다. |
| "하위 역할이 못 알아들을까 불안하다" | 불안은 코드 대필로 해소되지 않고, 검증이 약하다는 신호다. | 검사 명령과 수용 기준을 강화한다. 그래도 어려우면 「구현 등급」에 따라 Senior에게 배정한다. |
| "재작업 지시니 고친 코드를 주자" | 수정의 작성자가 배정자로 바뀌고, 재검토가 자기 검토가 된다. | finding에 결함, 재현 방법, 기대 동작을 적는다. |

## 예외

- **하위 역할이 없는 실행:** 실행 깊이 1이거나 역할을 이어받아 산출물을 직접 만들어야 하는 경우에는 이 규율이 적용되지 않는다. 그때는 배정이 없으므로 대필도 없다.
- **계약 자체인 코드:** 공유 타입 선언, 스키마, 설정 키처럼 여러 task가 똑같이 따라야 하는 계약은 지시문에 그대로 적는다. 다만 선언에 그치고 동작하는 본문은 넣지 않는다.
- **위치 지정:** 기존 코드를 인용해 "이 부분을 바꾼다"고 가리키는 것은 대필이 아니다.

## 역할별 적용 지점

| 역할 | 적용 시점 | 핵심 행동 |
|------|----------|----------|
| PM | task 작성·재작업 지시 | `instruction`에는 인터페이스와 기대 동작만 쓰고, 불안하면 검사와 수용 기준을 강화한다. |
| PL | 분할·통합 충돌 반환 | 분할 계획과 충돌 반환에 해결 코드를 넣지 않고 충돌 파일과 조건만 넘긴다. |
| Senior | 설계 결과·검토 finding | 설계는 인터페이스·순서·실패 조건까지 쓰고, finding은 결함과 기대 동작으로 쓴다. |
| Junior | 구현 | 받은 지시문에 완성된 구현이 들어 있으면 수용 기준과 검사로 결과를 확인하고, 옮겨 적었다는 사실을 보고한다. |
