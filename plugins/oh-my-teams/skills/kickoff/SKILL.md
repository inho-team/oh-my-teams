# 팀 작업 시작

사용자의 요청을 받은 현재 세션이 작업의 소유자다. 별도의 이사나 PM 세션을 열지 않는다. 먼저 [세션 소유권 구조](../../references/architecture.md)를 읽고, 사용 중인 Orca CLI의 `orca-cli` 가이드를 확인한다. Orca 워크트리의 경로와 전체 ID, 현재 세션을 조회한다. 확인되지 않은 워크트리를 소유한다고 보고하지 않는다.

## 시작

1. [작업 흐름](../../references/task-workflow.md#요청을-구성한다)에 따라 목표, 측정 가능한 수용 기준, 제약, 필수 검사와 전달 범위를 사용자 요청과 저장소 지침에서 구성한다. 이미 받은 허가는 보존하며 결과를 바꾸는 정보가 없을 때에만 소유 세션이 사용자에게 묻는다.
2. 같은 목표를 이미 진행 중이면 현재 워크트리와 Git 상태에서 이어서 진행한다. 기록을 찾지 못했다는 이유로 새 워크트리를 만들지 않는다.
3. 사용자가 Goal 생성을 명시적으로 요청했고 호스트가 지원한다면 현재 소유 세션에서 하나를 만든다. 별도 실행 루프를 중복으로 시작하지 않는다.
4. 순차 편집과 일반 검사는 현재 워크트리에서 수행한다. 읽기 전용 조사와 판단이 필요하면 [consult](../consult/SKILL.md)에 따라 전문 서브에이전트를 호출할 수 있다.
5. 독립적인 동시 편집이 필요할 때에만 Orca 자식 워크트리에 새 소유 세션을 연다. 작업 범위, 기준 커밋, 완료 조건과 보고 대상을 전달하고 Orca에서 감독한다. 공유 매니페스트, 잠금 파일과 버전 파일은 결과를 통합하는 소유 세션만 수정하도록 자식의 범위에서 제외한다. 배정은 편집 범위를 정할 뿐 전달이나 병합 권한을 주지 않는다. 읽기 전용 검토만을 위해 새 워크트리를 만들지 않는다.

자식 세션을 열기 전에는 CLI가 현재 앱과 같은 Orca 런타임·실행 호스트를 가리키고, 대상 워크트리가 그 앱의 관리 대상인지 확인한다. 점검 항목과 판정은 [환경 진단](../../references/diagnostics.md)을 따른다. 에이전트 실행은 해당 버전의 `orca-cli` 가이드가 안내하는 경로로 수행하며 셸 터미널 생성만으로 에이전트 실행을 대신하지 않는다. 실행 응답의 세션·터미널 핸들을 Orca의 워크트리와 세션·터미널 목록에서 대조한다. 연결되지 않은 `orphaned` 상태이거나 앱에서 해당 작업의 탭·세션을 확인할 수 없으면 배정 완료로 보고하지 않는다. 앱·CLI 버전과 연결 대상, 기존 핸들을 보존하고 해당 버전이 지원하는 연결 복구 방법을 확인한다. 관측 실패만으로 같은 에이전트를 다시 실행하지 않는다.

## 진행과 종료

목표와 범위를 정한 뒤 작업 요청 본문은 [YAML 문서 규칙](../../references/documents/protocol.yaml)과 [JSON Schema](../../references/documents/document.schema.json)의 `task_request`로 작성한다. [검증 조건을 포함한 작업 예제](../../references/documents/verified-task.example.yaml)의 가상 값을 실제 값으로 바꾼다. 원래 수용 기준·필수 검사·전달 범위와 사용자 허가 근거를 보존하고, 필요한 CI·독립 검토·전달 증거를 `verification`에 기록한다. 사용자가 정리를 완료 조건으로 요구했다면 `cleanup_required`에 기록한다. 이 문서는 요청이며 Orca의 실행 상태를 복제한 등록부가 아니다. 사용자에게 문서로 보여줄 때는 검증한 같은 데이터에서 HTML을 생성한다.

한 워크트리에서는 소유 세션만 편집한다. 서브에이전트가 같은 파일을 병렬로 고치지 않는다. 자식 워크트리의 결과는 소유 세션이 커밋과 검사를 확인한 뒤 통합한다. 작업을 재개할 때에는 Orca의 실제 세션과 워크트리 상태, Git HEAD를 확인하고 같은 일을 중복 배정하지 않는다.

세션이 보이지 않거나 관측이 타임아웃된 경우에는 [실패 상황의 판단 기준](../../references/failure-handling.md)에 따라 기존 실행을 다시 확인한다. 관측 실패만으로 대체 세션을 만들지 않는다.

위임 직전, 자식 결과를 통합한 직후, 재개 직후와 범위 변경을 받은 직후에는 [목표 재대조 절차](../../references/task-workflow.md#목표를-다시-대조한다)에 따라 원래 목표와 현재 변경을 대조한다. 완료 전에 최신 결과와 수용 기준을 대조한다. 필요한 독립 검토는 구현과 다른 실행 ID가 고정된 커밋을 읽게 한다. 전달과 회수는 [close](../close/SKILL.md)를 따른다. 취소하거나 목표를 달성하지 못한 경우에는 [disband](../disband/SKILL.md)를 따른다.
