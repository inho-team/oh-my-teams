# 전문 서브에이전트 호출

이 스킬은 현재 Orca 워크트리의 소유 세션이 사용한다. advisor, lawyer, auditor는 상설 조직 역할이나 별도 워크트리가 아니다. 호출자는 [세션 소유권 구조](../../references/architecture.md)에 따라 작업을 계속 소유한다.

호스트가 서브에이전트를 제공하면 목적과 읽을 자료를 좁혀 호출한다. 제공하지 않으면 소유 세션이 같은 검토를 직접 수행하되, 독립 검토를 수행했다고 주장하지 않는다. 서브에이전트에게 워크트리·브랜치·커밋 생성, 파일 편집, 재위임, 사용자 연락과 승인 기록을 맡기지 않는다.

사용자에게 직접 묻는 행위에는 `AskUserQuestion`이나 호스트의 동등한 도구로 선택 창·확인 창을 띄우는 것도 포함된다. 서브에이전트는 이런 창을 열지 않는다. 자료의 출처가 불명확하거나 권한·결정이 필요하면 확인한 사실, 막힌 이유와 필요한 결정을 기존 호출의 회신 채널로 소유 세션에 전달한다. 중간 보고 채널이 없으면 불확실성을 명시한 결과를 반환하고, 소유 세션이 사용자에게 질문할지 판단한다. 소유 세션은 회신에서 차단 원인을 확인하고 지시의 출처를 대조한 뒤 필요한 자료나 결정을 같은 호출에 전달한다.

## 요청과 결과 형식

호출자는 [검토 요청 구성 절차](../../references/task-workflow.md#검토-요청을-구성한다)에 따라 변경 목적, 기준·대상 커밋, 원래 수용 기준과 관련 위험에서 요청을 구성한다. 설계 선택이나 결과 대조가 필요할 때에만 호출하며, 사용자에게 이미 확인한 배경을 다시 요구하지 않는다.

검토 요청 본문과 회신은 [YAML 문서 규칙](../../references/documents/protocol.yaml)과 [JSON Schema](../../references/documents/document.schema.json)를 따른다. 호스트 도구가 요구하는 인자는 유지하고, 그 안의 OMT 메시지 본문을 YAML로 작성한다. [요청 예제](../../references/documents/review-request.example.yaml)와 [결과 예제](../../references/documents/review-result.example.yaml)의 가상 값을 실제 관측값으로 바꾼다. 결과의 `in_reply_to`와 검토 대상은 요청과 일치해야 하며, 다른 대상의 결과를 같은 요청의 승인으로 사용하지 않는다.

변경이 크면 한 요청에서 근거를 모두 확인할 수 있는 범위로 검토를 나눈다. 서로 독립된 모듈이나 수용 기준별로 요청을 분리하고, 나눈 요청은 모두 같은 `subject.commit`을 사용한다. 서로 독립된 읽기 전용 검토는 한 번에 요청하고, 결과를 기다리는 동안 같은 상태를 반복해서 조회하지 않는다. 이 규칙은 편집 작업의 병렬화에는 적용하지 않는다.

결과의 `findings`는 다음 기준으로 `severity`를 정한다. `high`는 보안 결함, 데이터 손실, 수용 기준 위반이나 잘못된 전달이다. `medium`은 기능 결함, 성능 저하나 필수 검사의 누락이다. `low`는 명명, 문서와 형식의 문제다. `high` 지적의 `description`에는 영향과 수정 방향을 함께 적게 한다.

소유 세션은 요청과 결과의 구조·의미 규칙, 근거와 실행 식별자를 확인한다. 사용자에게 검토 문서를 보여줄 때는 검증한 같은 데이터에서 HTML을 생성한다. 독립 검토 원문은 유지하고, HTML 표시 제약이 있으면 제약과 짧은 요약을 전달한다.

## advisor

계획, 설계 또는 장애 대응의 선택지가 실제로 갈릴 때 호출한다. 질문 하나, 관련 사실, 선택지와 제약을 전달한다. 답변에는 추천안, 근거, 반대 근거와 확인하지 못한 점을 요구한다. 최종 결정은 소유 세션이 내린다.

## lawyer

요구 사항이나 검토 이의에 대한 응답을 준비할 때 호출한다. 원문, 이의, 관련 커밋과 증거를 전달하고 각 주장에 대한 근거와 응답 초안을 요구한다. 타당한 이의는 인정하게 하며, 확인되지 않은 사실은 분리하게 한다. 소유 세션이 실제 파일을 확인하고 응답한다.

## auditor

수용 기준과 구현 결과를 독립적으로 대조할 필요가 있을 때 호출한다. 구현에 참여하지 않은 다른 실행 ID가 고정된 커밋을 읽게 한다. 기준별로 확인한 근거, 재현 가능한 결함, 누락과 남은 불확실성을 보고하게 한다. 소유 세션은 원문 결과를 보존하고 지적을 해결한 뒤 새 커밋을 다시 검토받는다. 같은 실행에서 자기 결과를 독립 검토로 승인하지 않는다.

auditor는 수용 기준과 함께 다음 사항을 확인하게 한다.

- 문서에 적은 개수와 지원 범위가 코드·테스트와 일치한다.
- 문서가 인용한 경로와 명령이 실제로 존재한다.
- 항상 통과하는 테스트나 이유를 밝히지 않은 skip이 없다.
- 추적 근거가 없는 스텁이 없고, 설계 메모나 미구현 기능을 구현된 결과로 표기하지 않았다.
- `--no-verify` 같은 검사 우회나 근거 없는 대량 삭제가 없다.

서브에이전트가 읽기 전용으로 검토하더라도 같은 워크트리의 편집 소유권은 호출자에게 남는다. 검토 기준이 되는 커밋이 바뀌면 이전 검토를 최신 결과의 승인으로 사용하지 않는다.
