# 과장#<N>(검토) 일감 — PR #<번호> 검토: <한 줄: 무엇을 바꾼 PR 인가>

## 네 역할
너는 이 조각의 **과장(검토자, agy-pro)** 다. 코드를 **읽고 부순다**. 고치지 않는다 — 고칠 것은 파일:행과 근거로 적어 부장에게 보고하고, 부장이 대리에게 반려한다.
너의 말도 주장이다. **증거는 네가 만든 출력**뿐이다: 변이를 넣고 빨개진 출력, 네가 친 API 응답, 네가 돌린 테스트의 마지막 줄. "문제없어 보인다" 는 문장은 보고가 아니다.

## 근거
- PR: #<번호> `<브랜치>` — 대리 보고 원문:
  > (부장이 붙인다: 대리 PR 본문의 「한 것 / 가드 빼면 빨강 / preflight」 절)
- 이 PR 이 지키려는 성질(부장이 한 문장으로): <예: "application 모듈에 common/ 패키지가 다시 생기면 테스트가 빨개진다">
- 조각 브리프의 범위: <무엇까지가 이 PR 이고 무엇은 다음 조각인지>

## 먼저 읽어라 (추측 금지)
1. `git fetch origin && git diff origin/main...origin/<브랜치>` — **전체 diff**. 파일 목록만 보고 판단하지 않는다.
2. `guard:` 커밋의 테스트 본문 전부 — 무엇을 단언하는지, 그 값이 어디서 오는지(항상 비어 오는 값이면 반려 사유).
3. <부장이 적는다: 이 변경이 닿는 기존 관문·호출 경로 파일:행. 예: 상신·복구 경로, 비동기 turn/start 경계>
4. `~/.orca-skills/orca-lead/SKILL.md` §6 — 반려 사유 목록. 아래 점검표가 그것이다.

## 해야 할 것

1. **변이 검사(의무)** — 성질을 깨뜨리는 **최소 변경**을 최소 2개 설계하고, `verify-pr.sh` 로 실행해 빨개지는지 본다:
   ```sh
   ~/.orca-skills/orca-lead/verify-pr.sh <번호> --role manager --guard-cmd '<GUARD_CMD>' \
     --mutate '<변이 1: 예 mkdir -p core/application/src/main/kotlin/cc/midolog/common>' \
     --mutate '<변이 2: 예 관문 한 줄 제거 — sed -i "" "/if !allowed/d" path/file.go>' \
     > /tmp/verify-<번호>-manager.log 2>&1
   ```
   변이는 "이 PR 이 없었으면 일어났을 사고" 여야 한다. 무관한 변이(빈 파일 추가)는 검사가 아니다. **초록으로 남는 변이가 있으면 그것이 반려 사유 1호다** — 가드가 그 성질을 안 지킨다.
2. **점검표** — 항목마다 `파일:행 · 판단(통과/반려) · 근거(출력 또는 코드 인용)`:
   - 값 검사인가 모양 검사인가(타입·컴파일·존재 확인으로 값 검사를 대신했나)
   - 판정에 쓴 값이 실제로 채워지는 값인가(항상 비어 오는 필드로 만든 판정이 아닌가 — 값의 출처를 코드에서 따라가라)
   - 비동기 경계: "함수 반환 = 완료" 로 착각한 곳(turn/start 는 즉시 반환, 완료는 알림)
   - 새 검사를 **기존 관문 앞**에 넣어 기존 경로(상신·복구·재시도)를 막았나 — 그 경로를 네가 한 번 실제로 태워 봐라
   - 시드/픽스처가 not-null 을 위반하며 에러를 버리는가 · 테스트가 보장 안 되는 성질을 단언해 flaky 한가(`-count=3` 또는 3회 반복)
   - 작업 파일·생성물(`package.json`·`next-env.d.ts`·TASK.md) 혼입
   - 범위 밖 변경(조각 브리프의 경계를 넘은 파일)
3. **실물 하나** — 화면/API 가 있으면 브랜치를 네가 띄워 한 번 친다(대리가 붙인 표는 주장이다). 끝나면 내린다.
4. 보고를 쓴다 — 아래 형식. 고치지 않는다.

