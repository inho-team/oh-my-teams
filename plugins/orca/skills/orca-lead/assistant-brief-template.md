# 대리#<N>(<기능>) 일감 — <조각 이름> (과장 → 대리)

## 네 역할 — 분할·통합·어려운 로직 (2026-09-13 배치: 과장 pro → 대리 flash → 사원 gpt-oss)
너는 이 조각의 **대리(agy-flash)** 다. 코드는 **사원(gpt-oss 하네스)** 이 먼저 쓴다. 네 일은 (1) 조각을 사원 크기로 **잘라** 일감 파일을 쓰고, (2) `pipeline-run.sh` 로 사원에게 차례로 시키고, (3) 사원이 못 넘긴 일감을 **네가 직접** 하고, (4) **통합**(전체 검사·교차 영향·guard/refactor/docs 커밋 정리·preflight·PR)해 과장에게 보고하는 것이다. 처음부터 네가 다 짜지 마라 — 네 시간은 사원이 못 하는 데에만 쓴다.
읽을 것: `~/.orca-skills/orca-worker/SKILL.md`(재현→고침→가드·preflight·PR 규칙), `~/.orca-skills/orca-lead/staff-brief-template.md`(사원 일감 형식).

## 순서
1. **읽기**: 아래 「조각의 목표·근거」 의 「먼저 읽어라」 를 전부 읽는다. 브랜치를 딴다: `git checkout -b <브랜치>`.
2. **분할**: 일감 디렉터리 `<일감 디렉터리>`(워크트리 **밖**)에 `task-01.md, task-02.md, …` 를 `staff-brief-template.md` 형식으로 쓴다. 규칙:
   - 일감 하나 = 파일 1~2개 편집 + **완료 조건이 테스트/셸로 판정**(순서·빈 줄·컴파일·테스트까지). 조건이 느슨하면 틀린 결과가 통과한다 — 이것이 네 일의 핵심이다.
   - 순서: `guard:` 테스트 먼저(구현 없이 빨강이어야 함 — 조건에 그렇게 적지 말고, 테스트 파일 존재·컴파일만 조건으로), 그 다음 구현(조건: 그 테스트가 초록), 그 다음 문서.
   - **병렬(네 판단)**: 파일이 겹치지 않는 일감은 같은 번호에 글자를 붙여 한 묶음으로 둔다 — `task-02a.md`, `task-02b.md`. 파이프라인이 임시 작업 공간에서 동시에 돌리고 커밋을 네 브랜치에 순서대로 올린다. 번호가 다르면 순차(앞 일감 결과 위에서 돈다). 같은 파일을 만지는 일감을 한 묶음에 넣지 마라 — 넣으면 뒤 것이 충돌로 남는다(실측).
   - 커밋 메시지 접두사: `guard:` / `refactor:`·`feat:`·`fix:` / `docs:`.
   - 편집 지시에는 파일 경로·위치·본보기 파일(`cat` 으로 읽으라고)·넣을 텍스트 전문을 적는다. "적절히" 같은 말은 쓰지 않는다. 위치·본보기를 찾는 읽기는 파일을 다 열지 말고 `~/.orca-skills/orca-lead/staff-find.sh <저장소 절대 경로> "<질문>" --paths <경로 힌트>` 로 사원에게 — 대조 통과한 파일:행만 온다(14초 실측).
3. **실행**: `~/.orca-skills/orca-lead/pipeline-run.sh <워크트리> <일감 디렉터리> --branch <브랜치> --notify <네 터미널> > /tmp/pipeline-<조각>.log 2>&1 &` 로 배경 실행하고 프롬프트로 돌아간다. 끝나면 `[pipeline …]` 한 줄이 온다(일감당 1~4분). 네 터미널 핸들은 `orca terminal show --json` 의 `handle`.
4. **실패 일감**: 사원은 일감마다 gpt-oss 5회 → flash 2회 사다리를 탄다(통과 뒤 검수 사원이 추가 검사·변이를 돌려 미달이면 1회 반려). 그래도 🔴 인 `PIPELINE.md` 일감은 **네가 직접** 들어가 확인하고 한다(같은 브랜치, 일감 파일의 편집 지시·완료 조건 그대로, 완료 조건을 네가 돌려 확인). 로그 `/tmp/pipe-<워크트리>-task-NN.harness.log` 에 사원·검수·대리(사다리)가 무엇을 틀렸는지 있다.
   - 🔴 가 **cherry-pick 충돌**이면 커밋은 이미 `pipe/task-NN` 브랜치에 있다 — `git cherry-pick <sha>` 로 네 브랜치에 올리며 충돌만 풀고(완료 조건 다시 확인), `git branch -D pipe/task-NN`.
5. **통합**: 전체 검사(`<CHECK_CMDS>`)를 필터 없이 돌린다 → 교차 영향(일감 사이 import·이름 충돌)을 고친다 → 가드를 빼고 돌려 빨개지는지 각 가드마다 확인(출력) → `~/.orca-skills/orca-worker/preflight.sh '<검사…>'` 🔴 0 → push → `gh pr create --base main --body-file <파일>`(본문: 한 것 / 안 한 것 / 가드 빼면 빨강 출력 / **PIPELINE.md 표** / preflight 출력 / 내린 것).
6. **보고**: 과장 Run 으로(아래 공통 규칙의 `--run`). 제목 `대리 완료 — PR #<n> (<조각>)`, 본문에 PIPELINE.md 표(사원/대리 누가 몇 회에 했나)를 붙인다.

## ⚠️ 함정(실측)
- 일감 디렉터리를 워크트리 안에 두면 하네스의 `git clean`/`add` 에 휩쓸린다 — 반드시 밖(`~/.<프로젝트>/coord/tasks-<조각>/`).
- 사원은 문자열 이스케이프·순서·빈 줄을 자주 틀린다. 완료 조건이 그것을 잡아야 사다리가 돈다(`grep -A1`, 줄 수, 컴파일). 검수 사원은 보강일 뿐이다 — 「빈 줄 정확히 하나」 같은 조건은 네가 적어야 잡힌다(실측).
- `pipeline-run.sh` 를 앞에서 돌리지 마라 — 배경 + `--notify`.
- 실패 일감을 네가 할 때도 **완료 조건은 그대로** 지켜라(네가 다르게 만들면 검토 때 걸린다).
